# Аудит-ревизия после 6.3.3 — корректность реализации и остаточные дефекты

Дата: 2026-10-16
База: `main` = `58e4aad` (6.3.2b + 6.3.3 закоммичены и запушены).
Характер работы: **только аудит, без изменений кода** (по указанию владельца).

Направления (от владельца):
1. Другие места, где частичный результат выдаётся за полный.
2. Отображение операций с неизвестным исходом в интерфейсе.
3. Согласованность контрактов провайдеров и фоновых работников после нескольких этапов.
4. Проблемы жизненного цикла работников и устаревших ответов.

## 1. A1 (MEDIUM): PVE `_await_task` — «нет UPID» = «успех»

```python
# backend/core.py:81-83
upid = result.get("data", result) if isinstance(result, dict) else result
if not (isinstance(upid, str) and upid.startswith("UPID:")):
    return True, ""
```

Все 20+ вызовов `_await_task` — заведомо **асинхронные** операции PVE
(resize диска, move disk, snapshot create/remove, clone, migrate, delete VM,
restore, upload; комментарии в коде сами объясняют, что await нужен, чтобы
«failed resize не выглядел успехом»). При этом ответ без UPID (деградированный
200, прокси, нестандартная сборка) молча читается как синхронный успех —
операция могла быть запущена и продолжаться.

Это **тот же класс дефекта**, что устранён в 6.3.3 для PBS (честный запуск,
§4.1 отчёта 6.3.3) и в D12 (неоднозначный тайм-аут legacy-заданий): частичный
или деградированный ответ выдаётся за полный результат, только с обратным
знаком — здесь фальшивый *успех*, а не фальшивый провал.

Существенное отличие от PBS: у части PVE-эндпоинтов (DELETE снапшота,
обновление конфигов) `data: null` — легитимный синхронный успех. Проверено:
такие операции **не** проходят через `_await_task` (обновление/удаление
backup-заданий идут напрямую, D12-обёртки отдельно). Среди вызовов
`_await_task` синхронно-успешных ответов по контракту PVE не существует.

Статус: Подтверждено кодом (перечитаны все вызовы; практический триггер —
деградированный ответ сервера, редкий, но вся серия аудитов именно об этом
классе).

Рекомендация: в `_await_task` добавить параметр `expect_upid=True` для
известно-асинхронных операций; при `expect_upid` и отсутствии UPID —
возвращать `(False, "task outcome unknown — response did not contain a task
id")` (семантика poll_failed, санитизация как у соседних веток). Миграция
механическая: сигнатура с дефолтом, ретро-совместимо.

## 2. A2 (MEDIUM): Fleet Health runway — тихая деградация алармов

`_runway()` (`fleet.py:230-238`): сбой `rrddata` для конкретного хранилища →
`continue` → оценки нет. `_runway_rows()` (`fleet_health.py:365-392`)
обходит **только** `bundle.runway`, поэтому:

- пропадает не только прогноз «дней осталось», но и фоллбэк «Storage almost
  full» по фактическому заполнению (он живёт внутри той же строки оценки);
- «нет строки» в разделе неотличимо от «прогноз хороший» — и от «данные не
  читаются» (след — только `logger.debug`).

Для сравнения: compliance- и PBS-разделы того же диалога показывают «нет
данных» жёлтой строкой «unverified» (паттерн D4: отсутствие свидетельства —
не подтверждённое отсутствие). Runway этот паттерн не применяет.

Статус: Подтверждено кодом.

Рекомендация: при сбое rrddata (и/или дегенеративной серии) добавлять в
`bundle.runway` запись-заглушку с признаком «unavailable» и рендерить её
нейтральной/жёлтой строкой «Runway unavailable: {storage}/{node}» — по образцу
«PBS freshness unverified» (fleet_health.py:257-262).

## 3. A3 (LOW): кластер может исчезнуть из выдачи Fleet Health

`FleetHealthWorker._run` → `job()`: исключение из `_collect_one` ловится и
`return` без добавления результата — кластер не попадает в `finished_all`.
Нормальный путь (ошибка сети/провайдера) обрабатывается **внутри**
`_collect_one` (строка-CollectError в отчёте ✓). Уязвим только случай, когда
упала сама except-ветка (импорт/построение отчёта) — вероятность низкая, но
контракт «диалог получает сигнал по каждому кластеру» (D5-эра) в этом пути
не держится: диалог отрисуется без кластера и без объяснения.

Статус: Подтверждено кодом.

Рекомендация: в `job` при исключении добавлять бандл-заглушку с
`CollectError(name, "cluster", str(e))` — как это уже делает `_collect_one`.

## 4. Направление 2: неизвестный исход в UI

### B1 (LOW): «still running» через «failed»-ключи

`_await_task` при клиентском дедлайне возвращает `(False, "still running
after {N} s")` — честно по сути, но потребители показывают это через ключи
вида `tr("Restore failed: {err}")` (vmops.py:479), аналогично snapshot/clone/
upload-воркеры. Итог в UI: «Restore failed: still running after 120 s» —
операция не провалена и продолжается, а формулировка говорит об обратном.
Таксономия `_await_task` (failed / poll_failed / timeout) известна только
внутри core; воркеры получают единый `(ok, err)` и не могут отличить
«провал» от «продолжается».

Статус: Подтверждено кодом (конкретные ключи показаны).

Рекомендация: вернуть статус наружу (например `_await_task` → `(status,
detail)` в терминах TaskAPI или добавить флаг), в воркерах для `timeout`
использовать отдельный ключ `tr("Task still running after {n} s — check the
result later")` и **не** сбрасывать кнопки в ошибочное состояние там, где
это имеет значение.

### B2 (INFO): PBS-сторона — покрыта

Проверено: run/verify → трекер с полным набором исходов (в т.ч. «исход
неизвестен» и «наблюдение прервано»); лимит трекеров и дубликат UPID —
честные сообщения; устаревшие ответы чужих серверов отсечены; уничтожение
панели безопасно. Сообщения PBS-клиента английские — устоявшаяся конвенция
транспортного слоя (как и у PVE-текстов задач), дефектом не считаю.

## 5. Направление 3: контракты провайдеров и воркеров — согласованы

Проверено, дефектов не найдено (INFO):

- `PbsProvider` содержит все методы, запрашиваемые панелью через
  `PbsApiWorker` (`_start`: datastores, snapshots, jobs, namespaces,
  verify_datastore, forget_snapshot, run_job); новый `jobs() ->
  (jobs, failed_kinds)` распаковывается ровно в одном обработчике.
- Сигнатуры сигналов/слотов: `PbsApiWorker` (done/failed/finished),
  `_TrackerSignals` (update/finished), `HostTokenDeleteWorker`
  (delete_result/finished) — арности сходятся во всех точках подключения;
  отказ пула (`run_worker -> False`) обрабатывается на местах (D8 не
  разрушился).
- `create_provider` диспетчеризует по `cfg["type"]`; Fleet Health цели
  исключают pbs/skip/`_ambiguous` (`build_fleet_targets`) — универсальные
  `provider.rrd`/`provider.tasks` к PBS-конфигам не применяются.
- `TaskAPI.poll` таксономия (stopped/poll_failed/timeout) полностью
  покрывается в `_await_task`, включая defensive else.
- `datastores_loaded(server, stores)` эмитится только при совпадении
  сервера, с именем **из тега**; `tree_panel.set_pbs_datastores` ключует
  элементы по `(pbs, server)` — устаревший ответ не попадает в чужой узел.

## 6. Направление 4: жизненный цикл и устаревшие ответы

### D1 (LOW): выход приложения при активном трекере

Трекеры и `PbsApiWorker` живут в `QThreadPool.globalInstance()`; Qt при
выходе дожидается потоков пула. Активный трекер спит до `interval` (3 с)
между тиками и может задержать завершение приложения; `stop_event`
взводится только на `destroyed` панели, а при выходе разрушение виджетов
может не успеть произойти до ожидания пула.

Статус: механика подтверждена кодом (глобальный пул, sleep в трекере);
сам факт задержки — Гипотеза (зависит от порядка разрушения Qt при выходе).

Рекомендация (низкий приоритет): на `QApplication.aboutToQuit` взводить все
stop-события (панель уже умеет: `_stop_all_trackers`).

### D2 (INFO): проверено и в порядке

- `WorkerManager`: отказ «пул+очередь полны» не оставляет воркер в
  `_pending` (чистый drop + honest on_overload); `discard_worker`
  идемпотентен; `finished -> discard` в `_try_start` подключается до старта.
- `FleetHealthWorker` — daemon-поток, join ограничен `JOIN_TIMEOUT_S`,
  `finished_all` эмитится всегда (диалог не зависает с кнопками).
- Реестр трекеров панели чистится по `finished` с identity-проверкой
  (чужой `finished` реестр не трогает).
- Stale-гейты панели PBS: ds/snap/ns/jobs (по серверу; snap — ещё по store
  и namespace), verify/run — по серверу (добавлено в 6.3.3).

## 8. Вывод

Реализация 6.3.3 (и контрактные решения 6.3.2b) ревизию выдержала: PBS-путь
честен во всех проверенных точках, контракты воркеров/провайдеров после пяти
этапов правок не разъехались, жизненный цикл (D5–D9) не деградировал.
Остаточные дефекты сосредоточены на **PVE-стороне** и в **Fleet Health**:
A1 — последний представитель класса «деградированный ответ = фальшивый
результат» в `_await_task`, A2 — тихая деградация алармов runway. Оба —
кандидаты на следующий точечный этап (по объёму — уровень 6.3.2b, не больше).
