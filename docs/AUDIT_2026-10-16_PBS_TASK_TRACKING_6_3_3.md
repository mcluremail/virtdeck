## 3. Контракт PBS API — подтверждения

Для форматов ответов использованы **исходники PBS** (`src/api2/node/tasks.rs`,
ветка master на github.com/proxmox/proxmox-backup) — веб-оболочка API-viewer
статического текста не содержит.

| Вопрос | Ответ | Статус |
|---|---|---|
| Что возвращает `GET /nodes/{node}/tasks/{upid}/status` | объект: `upid, node, pid, pstart, starttime, type, id, user` всегда; `status` = `'running'`/`'stopped'`; у остановленных — `exitstatus` = `'OK'` / `'Error: <msg>'` / `'unknown'` | Подтверждено доступной документацией (исходники PBS, схема ответа `get_task_status`) |
| Кто может читать статус | владелец задачи всегда; прочим нужен `Sys.Audit` на `/system/tasks` | Подтверждено доступной документацией (там же, Permission) |
| Формат UPID | `UPID:{node}:{pid}:{pstart}:{starttime}:{wtype}:{wid}:{authid}` — двоеточия обязательны → URL-кодирование пути | Подтверждено доступной документацией (`UPID` в pbs-api-types; формат того же семейства, что у PVE в `domain/fleet.py`) |
| Узел PBS | PBS однодневный; `GET /nodes` возвращает список из одной записи с `name` (реальное имя хоста); `localhost` — допустимый алиас | Подтверждено доступной документацией (в `list_tasks` PBS сам пишет `node: "localhost"`) |
| Что возвращает `POST .../run` | UPID-строка в `data` | Подтверждено кодом (предшествующий контракт) + документацией PBS |

**Расхождение с прежним отчётом.** Исследование D16 в отчёте 6.3.2b (§7)
предполагало у PBS поле `exitcode` (целое). Фактически PBS использует строку
`exitstatus` (`'OK'` / `'Error: <msg>'` / `'unknown'`). Реализация следует
первоисточнику; гипотеза 6.3.2b снята.

## 4. Клиент (`virtdeck/pbs/client.py`)

### 4.1 Честный запуск — `_start_task()`

`run_job()` и `verify_datastore()` теперь сводятся к `_start_task(path)`:

| Ситуация | Поведение | Обоснование |
|---|---|---|
| 200, `data` — непустая строка | возвращается подтверждённый UPID (`.strip()`) | «подтверждённый запуск» — есть идентификатор задачи |
| 200, `data` = null / `""` / не строка | `PbsError("job start outcome unknown: the server accepted the request (HTTP 200) but the response does not contain a task id (UPID) — check the task list on the server", 200)` | сервер мог принять запрос — успехом это читать запрещено; авто-retry недопустим (риск двойного запуска) |
| транспортная ошибка при имеющемся тикете (`status_code == 0`) | `PbsError("job start outcome unknown (the request was not confirmed): …", 0)` | запрос был отправлен (или мог быть) — исход неизвестен |
| дефинитивные HTTP-ошибки (401 после relogin, 403, 4xx/5xx) | проходят без обёртки | запрос точно не выполнен — «исход неизвестен» был бы дезинформацией |

Проверка `had_ticket` (был ли тикет до вызова) отделяет «транспорт в полёте»
от «упал ещё при логине»: если тикета не было — ошибка логина означает, что
стартовый запрос вообще не отправлялся, и обёртка не применяется. Граничный
случай (тикет был, relogin упал по транспорту) консервативно помечается как
«неизвестно» — безвредно-честное направление. Тело ответа и секреты в текст
ошибки не попадают (тест).

### 4.2 Статус задачи и узел

- `task_status(node, upid)` — `GET /nodes/{node}/tasks/{upid}/status`; оба
  сегмента через `_q()` (двоеточия и `/` в UPID кодируются — тест). Ответ,
  не являющийся объектом, — ошибка чтения, а не статус.
- `node_name()` — первый валидный `name` из `GET /nodes`; кэш на клиенте
  (один провайдер на воркера → один запрос за жизнь). Пустой/битый список —
  `PbsError("could not determine the PBS node name …")`.
- `forget_node()` — сброс кэша для сценария устаревшего имени (§5).

Минимальный набор запросов на тик опроса: один `GET …/status` (`/nodes` —
один раз на воркера, из кэша). Лог задачи (`GET …/log`) не читается — вне
срока этапа (§9).

## 5. Провайдер (`virtdeck/pbs/provider.py`)

`task_status(upid) -> (state, detail)` — один шаг чтения состояния, таксономия
как у PVE (`provider/_tasks.py`), без связи транспорта:

| Ответ PBS | Возврат |
|---|---|
| `status == "running"` | `("running", "")` |
| `stopped` + `exitstatus == "OK"` | `("success", "")` |
| `stopped` + `exitstatus.startswith("Error")` | `("failed", exitstatus)` |
| `stopped` без читаемого `exitstatus` (или `'unknown'`) | `("unknown", "task stopped but exit status is unavailable")` — **терминальное** «неизвестно», не угадываем в успех/провал |
| объект без `status` / нечитаемая форма | `PbsError` — **повторяемая** ошибка чтения (бюджет ретраев трекера), а не вердикт |
| HTTP 404/400 при вызове статуса | кэш узла сбрасывается, узел резолвится заново, **одна** повторная попытка (только чтение — безопасно); прочие коды — без ретрая |

Правило этапа соблюдено: «сбой чтения статуса» ≠ «провал задачи» — провалом
считается только подтверждённый `Error: …`.

## 6. Трекер (`virtdeck/pbs/workers.py`)

`PbsTaskTracker(QRunnable)` — не новая система управления задачами, а ещё один
QRunnable-потребитель существующей PBS-инфраструктуры воркеров (запрет ТЗ
соблюдён).

- **Сигналы пер-инстансные** (`_TrackerSignals`: `update(key, (state, detail))`,
  `finished`) — механика 6.3.2a D9; подключение выполняется **до** старта
  пула, поэтому быстрое завершение не может обогнать подписку (сценарий §8
  в текущей архитектуре невозможен — зафиксировано в докстринге и тестом
  connect-before-start не требуется).
- `run()`: создаёт свежий `PbsProvider` (как `PbsApiWorker`), опрашивает,
  в `finally` закрывает провайдера **ровно один раз** (тест) и эмитит
  `update` + `finished` **ровно один раз** (тесты), даже при падении
  конструктора провайдера.
- `_poll()`: паузы (`time.sleep(interval)`) только внутри воркера; `interval`,
  `deadline`, `max_read_failures` инъекцией — в тестах `interval=0.0`,
  никакого реального ожидания.
- Исходы:
  - подтверждённый терминал от провайдера → `success`/`failed`/`unknown` (терминальное);
  - 401/403 → сразу `("unknown", "status not readable (authentication or rights)…")` —
    не исцеляется опросом и не является провалом задачи (§4 ТЗ);
  - прочие ошибки чтения — до `max_read_failures=5` подряд, затем `("unknown", "status unreadable: …")`;
  - дедлайн (`900 с` по умолчанию, проверяется после каждого тика) →
    `("timeout", "watch deadline reached — the task may still be running on the server")` —
    VirtDeck перестал наблюдать, но **не** утверждает провал;
  - `stop_event` (закрытие панели) → выход без эмитов, `finished` один раз.
- Детали сообщений прогоняются через `_short()` (одна строка, ≤300 символов).

## 7. Панель (`virtdeck/ui/pbs_panel.py`)

### 7.1 Полоска операций

Под стеком (видна на обеих страницах) — таблица `Operation | State | Detail`,
скрыта, пока нет операций для текущего сервера. Состояния:
`starting → running → {success | failed | unknown | timeout}` с цветами
(успех — зелёный, провал — красный, неизвестно/тайм-аут — жёлтый).
Завершённые результаты **сохраняются** (последние 8 на сервер; старейшие
вытесняются), активные никогда не вытесняются.

### 7.2 Реестр и жизненный цикл

- Реестр `self._trackers[(server, upid)] = (tracker, stop_event)`; дубликат
  UPID → заметка «This task is already being tracked», второй воркер не
  стартует (§6.8).
- Лимит `_MAX_PBS_TRACKERS = 8` — отдельный от `_MAX_PBS_WORKERS = 16`:
  трекеры долгоживущие и не должны блокировать короткие запросы данных.
  Превышение → честное «Tracking limit reached — the result will not be
  watched; check the server» (это не провал задачи, §6.4).
- Смена сервера: строки рендерятся только текущего сервера; апдейты/статусы
  чужих серверов игнорируются (`_on_tracker_update`, а также run/verify-ветки
  `_on_worker_done` — устаревший результат другого сервера ничего не пишет,
  §6.9; найдено при ревизии diff и покрыто тестами).
- Уничтожение панели: `destroyed → _stop_all_trackers()` (все `stop_event`
  взводятся — трекер завершается между тиками); слоты обёрнуты
  `try/except RuntimeError`, авто-отключение сигналов Qt при разрушении
  приёмника; тест с `deleteLater` + `DeferredDelete` подтверждает отсутствие
  обращений к мёртвым объектам (§6.10).
- Повторное открытие панели создаёт новый экземпляр с чистым состоянием;
  апдейты фильтруются по тегу сервера — попадание чужого ответа невозможно.

### 7.3 Интеграция запуска

- Тег run расширен: `("run", server, kind, id)` — нужен для подписи операции
  и фильтрации по серверу; verify-тег `("verify", server, store)` уже нёс
  нужное.
- После подтверждённого UPID: строка «Starting» + трекер + статус «Job
  started»/«Verify started» (теперь это **подтверждённый** факт) + обновление
  списка заданий.
- Контракт-дрейф-гард: если в `done` придёт не-UPID (теоретически невозможен
  при новом контракте клиента) — «Job start could not be confirmed…», без
  трекера и без «успеха».

## 10. Ограничения и что сознательно не входило

- **Лог задачи** (`GET /nodes/{node}/tasks/{upid}/log`) не читается и не
  показывается — подэтап D исследования 6.3.2b помечал его опциональным;
  ТЗ этапа 6.3.3 его не требует. Задел: `PbsClient.task_status` легко
  дополняется парным `task_log`.
- Права на чтение статуса чужих задач не проверяются в UI отдельно: трекер
  стартует только для задач, запущенных самим VirtDeck (владелец — тот же
  токен), а 401/403 отрабатываются как честное «неизвестно».
- Восстановление реестра трекеров после перезапуска приложения не выполняется
  (UPID не персистится): после перезапуска пользователь видит задания в
  списке Jobs, но наблюдение не возобновляется. Вне срока этапа.
- Мультиузловые PBS-кластеры: PBS однодневный, `/nodes` возвращает одну
  запись; при будущем мультиузле достаточно расширить `node_name()`.
