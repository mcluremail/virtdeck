## 1. Резюме и вывод о серьёзности

D5 подтверждён: карта «последний успешный бэкап» собирается один раз для всего
флота и применяется к гостям каждого кластера без привязки к источнику
(datastore/namespace/server). Ключ карты — только `(backup-type, backup-id)`,
т.е. `(vm|lxc, "VMID")`. **[код]**

Последствие: у двух независимых кластеров VMID почти всегда пересекаются
(оба нумеруются со 100), поэтому чужой снимок «vm/100» засчитывается гостю
второго кластера как его собственный свежий бэкап. Это **ложноположительное
подтверждение**: реальная протухлость/отсутствие бэкапа скрывается свежим
чужим временем. Обратный эффект (ложное «никогда не бэкапился») возможен
только при исключении — не обнаружен. **[код]**

Серьёзность:
- Один PVE-таргет — дефект непроявляем (вся карта принадлежит ему). **[код]**
- ≥2 таргета, **разные** PBS/datastore — дефект проявляется при любом
  пересечении VMID (почти гарантировано). Свежесть бэкапов обоих кластеров
  становится недостоверной — это подрывает главный вопрос Fleet Health
  «когда последний раз бэкапился». По шкале исходного аудита — **P1**.
- ≥2 таргета, **общий** datastore с раздельными namespace — то же.
- ≥2 таргета, общий datastore **без** разделения (легитимная схема «один
  PBS на два кластера»): коллизия остаётся даже в целевом решении на уровне
  (server, datastore, namespace) — требуется явная политика (см. §5, A3).

Итог: **P1** при ≥2 таргетах и раздельных PBS-хранилищах (наиболее
распространённая схема); P2 — только если владелец подтвердит, что PBS
не делится между кластерами, или кластеров один (см. открытый вопрос §8.1).

## 2. Фактическая цепочка данных

1. **Точка входа UI.** `virtdeck/ui/mainwindow.py:1567-1572`
   `_open_fleet_health` — PBS-конфиги берутся из **глобального** списка
   хостов приложения: `pbs_cfgs=[c for c in self.nodes_cfg if
   c.get("type")=="pbs" and not c.get("skip")]`. Привязки «PBS → кластер»
   в конфигах нет. **[код]**
2. **Диалог.** `virtdeck/ui/fleet_health.py:72-75,132-133` — держит
   `_pbs_cfgs` и передаёт в `FleetHealthWorker(targets, pbs_cfgs=…)`.
   **[код]**
3. **Общая карта.** `virtdeck/backend/fleet.py` `_run` (~124-139):
   **один** вызов `collect_pbs_last_backups(self._pbs_cfgs)` на весь флот;
   результат — общий `pbs_map` для всех таргетов. KNOWN LIMITATION-комментарий
   на месте (строки ~125-133). **[код]**
4. **Построение карты.** `virtdeck/fleet/pbs_source.py` (99 строк):
   на каждый PBS-конфиг → `PbsProvider` → `datastores()` → обход корневого
   namespace и вложенных (глубина ≤ `_MAX_NS_DEPTH = 3`) →
   `_add_snapshot` кладёт `{(backup_type, backup_id): ts}` (verify=ok только).
   Модель `PbsSnapshot` (`virtdeck/domain/pbs.py`) **хранит** `store` и `ns`,
   но построитель карты их **отбрасывает** — данные есть, ключ урезан.
   Изоляция источников соблюдается (упавший сервер/datastore не роняет сбор).
   **[код]**
5. **Прокидка в кластер.** `virtdeck/fleet/collector.py` `collect_cluster`:
   `pbs_last_backups` передаётся в `build_cluster_report` без изменений;
   storage-ряды собираются per-node из `list_node_storage` (сырые строки
   `GET /nodes/{node}/storage`, используется только usage/shared/active).
   **[код]**
6. **Точка ложной атрибуции.** `virtdeck/domain/fleet.py`
   `build_backup_states`: `pbs = pbs_times.get((_PBS_TYPE.get(vm_type),
   str(vmid)))` — lookup для **каждого** гостя каждого кластера в общей
   карте. Здесь чужой снимок становится «своим». Merge с задачами: max.
   **[код]**
7. **Отображение.** `virtdeck/ui/fleet_health.py:284-318`:
   свежесть PBS участвует в `last_successful` (маскирует протухлость/провал);
   при недоступной истории задач — жёлтый «Backup state unverified» (D4),
   при PVE<7.2 — caveat (D6). Механика «непроверенное ≠ красное» уже есть —
   её можно расширить на PBS-скоупинг. **[код]**

## 3. Контракты API и доступные поля

### 3.1 PBS-сторона (что уже доступно в коде) — **[код]**
- `PbsClient` (`virtdeck/pbs/client.py`): `/config/datastore`,
  `/admin/datastore/{store}/status`, `/admin/datastore/{store}/namespace?parent=`,
  `/admin/datastore/{store}/snapshots?ns=`.
- `PbsSnapshot` несёт `store`, `ns` (из поля `ns` ответа PBS), `backup_type`,
  `backup_id`, `backup_time`, `verify`. Т.е. **все размерности для скоупинга
  приходят с PBS-стороны**; теряются они только в построителе карты.
- Стенд: `tests/harness/fake_pbs.py` моделирует фильтр `ns` в snapshots
  (вложенные namespace listing'ом не отдаёт — при необходимости стенд дожать).

### 3.2 PVE-сторона (откуда взять привязку «кластер → (server, datastore, ns)»)

Ключевой результат этапа — **проверка гипотезы из KNOWN LIMITATION**.
Комментарий `backend/fleet.py` предполагал привязку «по хранилищам типа pbs,
на которые ссылается кластер» из per-node рядов. Исходники Proxmox это
опровергают:

- `GET /nodes/{node}/storage` строится функцией `PVE::Storage::storage_info`
  (pve-storage, `src/PVE/API2/Storage/Status.pm`, index → `storage_info`) и
  возвращает **только** `type, total, avail, used, shared, content, active,
  enabled` (+`used_fraction`, formats по запросу). Конфиг-свойства
  (`server`, `datastore`, `namespace`) в ряды **не попадают**. Проверено
  для master (PVE 9) **и** `stable-8` (PVE 8) — код идентичен по структуре,
  `$scfg` используется только для фильтрации (enabled/shared/target).
  **[док]** — pve-storage master и stable-8 (Status.pm, Storage.pm).
- `GET /storage` (конфиг-листинг, `src/PVE/API2/Storage/Config.pm`, index)
  возвращает **полные записи scfg**: `storage, type, digest, content, nodes, …`
  плюс все опции плагина — для pbs это `server, port, datastore, namespace,
  username, fingerprint, …`. `namespace` — **optional** (PVE≥7.2), отсутствие
  поля = корневой namespace `""`. Хелпер `api_storage_config` **не вычищает
  даже `password`** — ряды содержат секреты, логировать их целиком нельзя.
  **[док]** — pve-storage master и stable-8 (Config.pm; PBSPlugin.pm: options
  — `datastore` fixed, `namespace` optional).
- Практическое подтверждение на реальном PVE 8: штатный флоу VirtDeck
  «Storage → Edit» (`mainwindow.py:704-724` → `StorageConfigListWorker`
  (`backend/storage.py:295-315`, `cluster.list_storage_configs()`) →
  `StorageConfigDialog(config=…)`) предзаполняет форму из ряда `/storage`,
  включая поле `datastore` (и password для round-trip). **[код]**
- Провайдер **уже имеет** метод: `virtdeck/provider/_cluster.py:54-56`
  `ClusterAPI.list_storage_configs()` → `GET /storage`. Новый API-метод
  не нужен. **[код]**
- Форма редактирования pbs-хранилища в VirtDeck (`ui/storage_config_dialog.py:46`)
  знает `server, datastore, username, password, fingerprint`, но **не имеет
  поля namespace** — при фиксе namespace брать напрямую из рядов `/storage`
  (диалог не участвует в Fleet Health; отдельно отметить как соседний мелкий
  пробел UI). **[код]**

### 3.3 Сопоставление PBS-конфигов с рядами `/storage`

- Привязка по `storage`-ID **недостаточна**: ID локален для кластера, у
  PBS-сервера из глобальных конфигов VirtDeck общего имени нет. **[код]**
- Надёжный ключ: `(normalize(server), port|8007, datastore, namespace|"")`.
  `server` из ряда сопоставляется с `host` (+`port`) PBS-конфига VirtDeck
  (нормализация: lowercase, учёт порта). **[гипотеза]** в части вариаций
  написания хоста у владельца (FQDN vs IP vs shortname) — см. §8.2; сам
  принцип — **[док]** (PBSPlugin.pm: свойства `server`/`port`).
- owner-auth PBS (`auth_id`) для разделения кластеров ненадёжен (оба могут
  ходить под root@pam) — не используем. **[гипотеза]**, осознанно исключено.

## 4. Сценарии и текущее поведение

Классы исхода: ЛП — ложноположительное подтверждение бэкапа; ЛО —
ложноотрицательное; Н — непроверяемо (честно).

| № | Сценарий | Текущее поведение | Класс | Целевое поведение |
|---|---|---|---|---|
| S1 | 2 кластера, одинаковый VMID, разные datastore | Каждый гость получает max ts по `(vm,vmid)` со **всех** datastores — чужой свежий снимок засчитывается | **ЛП** | Каждый гость — только evidence своих bindings |
| S2 | Одинаковый VMID, разные namespace | То же (ns в ключе отсутствует) | **ЛП** | Скопинг по `(server,ds,ns)` |
| S3 | Несколько PBS-хранилищ у одного кластера (легитимно) | Внутри кластера дефекта нет (VMID уникален в кластере); риск — только через другой кластер (S1) | ок | Оба datastore разрешены |
| S4 | Один datastore доступен нескольким кластерам (легитимно) | Коллизия VMID → перекрёстные засчитывания | **ЛП** | При общем `(server,ds,ns)` и пересечении VMID — доказательство **не применяется**, статус unverified + caveat (A3) |
| S5 | Ряд `/storage` без `datastore`/`namespace` | — | Н (сейчас игнорируется) | `datastore` обязателен: binding не строится → PBS unverified для гостей этого хранилища; `namespace` optional → `""` |
| S6 | Недоступность `GET /storage` на одном таргете | — (сейчас map глобальная и «работает») | ок/ЛП | Только этот таргет: PBS unverified; остальные штатно. **Не** откатываться на глобальную карту |
| S7 | Запоздавший ответ со старой конфигурацией (storage.cfg изменился между сбором `/storage` и списком снимков) | окно ложной атрибуции | **ЛП/ЛО** (узкое) | Сбор bindings и PBS-карты в одном прогоне воркера; остаточный риск задокументирован |
| S8 | Подтверждённое отсутствие снимков (binding есть, ключа в scoped-карте нет) | — | Н | `pbs_last_ok=None` честно; «Never backed up» — только от задач, как в D4 |
| S9 | Непроверенное состояние ≠ «Never backed up» | Жёлтый unverified есть для tasks (D4); для PBS-скоупинга механики нет | Н | Расширить D4-механику: недоступный скоупинг → жёлтый caveat, не красный |
| S10 | Одинаковые имена хранилищ (storage ID) в разных кластерах с разными серверами | ID не участвует в сопоставлении снимков — коллизии имён сами по себе не вредят, но и не помогают привязке | Н | Привязка по `(server, datastore, ns)`, не по ID |

## 5. Предлагаемая архитектура

Принцип: **скопинг выполняется до domain-агрегации**, контракт domain не
меняется (`build_backup_states` продолжает получать плоскую
`{(type, vmid): ts}` — но уже отфильтрованную для конкретного кластера).

**A1. Многомерная карта** (`virtdeck/fleet/pbs_source.py`):
`collect_pbs_last_backups` возвращает
`{(server_key, datastore, ns): {(backup_type, backup_id): ts}}`, где
`server_key = (host.lower(), port)` — берётся из **PBS-конфига**, с которого
собирали (сам источник знаем, API не нужен). Внутренняя семантика (max ts,
verify=ok, изоляция источников) сохраняется. Это внутренний контракт
(`backend/fleet.py`, тесты pbs_source) — внешних потребителей нет. **[код]**

**A2. Привязки кластера** (`collector.py` / новый чистый селектор):
в потоке кластера — guarded-вызов `provider.cluster.list_storage_configs()`
(изоляция как у остальных источников; ошибка → источники не роняются);
из рядов `type=="pbs"` извлекаются bindings
`{(normalize(server), port|8007, datastore, row.get("namespace",""))…}`.
Ряды могут содержать секреты — в логи не попадают (логировать только имена
хранилищ). **[код]** + **[док]**

**A3. Селектор доказательств** (чистая функция, unit-тестируемая):
`select_pbs_evidence(pbs_map, bindings, all_target_bindings)` →
`(flat_map, scope_status, reasons)`:
- binding найден в карте → evidence из подкарты;
- binding'ов нет / сбор не удался → `scope_status="unavailable"`, пустая карта
  (НЕ глобальная!);
- **однозначность**: если одно и то же `(server_key, ds, ns)` разрешено ≥2
  таргетам и в обоих есть гость с тем же `(type, vmid)` → для этих гостей
  доказательство не применяется, `scope_status="ambiguous"` + caveat (S4).

**A4. Честность в отчёте** (`domain/fleet.py`): поле
`pbs_scope: "ok"|"unavailable"|"ambiguous"` (+reason) в `ClusterFleetReport`
или новый источник ошибки — по образцу D4. **[код]** (механика exists)

**A5. UI** (`ui/fleet_health.py`): при `scope != "ok"` — жёлтая строка- caveat
(«PBS freshness unverified: …»), красное «Never backed up» от PBS-отсутствия
не рендерится (S8/S9). i18n: новые ключи в 5 локалей, `_I18N_VERSION` 39→40.

Альтернативы (отклонены):
- **B: ручная привязка PBS→кластер в конфигах** — дублирует информацию, которую
  PVE уже отдаёт в `/storage`; лишний UI и места для ошибки. Отклонено.
- **C: привязка по per-node рядам `/nodes/{node}/storage`** — опровергнуто
  исходниками: свойств конфига в рядах нет (§3.2). KNOWN LIMITATION-комментарий
  при фиксе переписать.

Трейдоффы: +1 API-вызов на кластер (`GET /storage`, лёгкий); race S7
(остаточный, документируется); неоднозначность S4 остаётся для схемы «один
PBS на два кластера без разделения» — честно помечается unverified вместо
молчаливого кредита.

## 7. План тестов (T1–T10)

Единица: чистый селектор (tests/fleet), стенд fake_pve/fake_pbs, воркер-уровень (tests/ui).

1. **T1 = S1**: два таргета, одинаковый VMID, разные datastore → каждый гость
   получает только своё время (ничьи чужие).
2. **T2 = S2**: одинаковый VMID, разные namespace → только свой ns.
3. **T3 = S3**: один кластер, два PBS-хранилища → evidence из обоих.
4. **T4 = S4**: общий `(server,ds,ns)` у двух таргетов + пересечение VMID →
   доказательство не применяется, `scope="ambiguous"`, caveat в UI-модели.
5. **T5 = S5**: ряд pbs без `datastore` → binding отвергнут, unverified;
   ряд без `namespace` → binding с ns=`""` (валиден).
6. **T6 = S6**: `list_storage_configs` падает на одном таргете → его PBS
   unverified, второй таргет штатен; отчёт incomplete только у первого.
7. **T7 = S7**: bindings от старой конфигурации → используется снапшот на
   момент сбора; поведение зафиксировано тестом (документирующий).
8. **T8 = S8**: binding есть, снимков нет → `pbs_last_ok=None`; при живых
   задачах — зелёный по задачам; без задач — «Never backed up» только от задач.
9. **T9 = S9**: scope unavailable → жёлтый caveat, ни одной красной строки,
   выведенной из PBS-отсутствия.
10. **T10 = регрессия**: один кластер + один PBS, binding есть → pbs_last_ok
    совпадает с текущим поведением (обновить контракт-тесты
    `tests/fleet/test_pbs_source.py`, `tests/domain/test_fleet.py`,
    `tests/ui/test_fleet_health.py::test_worker_pbs_freshness`).

Критерий из §8.4 исходного аудита («тест §8.4») закрывается T1.

## 8. Неизвестные факты и открытые вопросы

1. **Топология владельца** (определяет P1/P2 и дизайн A3): сколько PVE-таргетов
   в флоте; делится ли PBS/datastore между кластерами; пересекаются ли VMID.
   — вопрос к владельцу.
2. **Нормализация хоста**: реальные значения `server` в storage.cfg (IP vs
   FQDN vs shortname) vs `host` PBS-конфигов VirtDeck. Если записи различаются,
   потребуется маппинг/ручное правило. **[гипотеза]** — проверить на стенде
   владельца или спросить.
3. **Используются ли namespace** в pbs-хранилищах владельца (PVE≥7.2) — влияет
   на тестовые сценарии T2/T4. **[гипотеза]**
4. **Секреты в рядях `/storage`**: исходник не вычищает `password` — при фиксе
   гарантировать, что ряды/логи не попадают в отчёты и логи целиком.
   **[док]**; поведение на конкретном PVE владельца — проверить при фиксе.
5. **Race S7** — остаточный риск; смягчается единым моментом сбора, полностью
   не устраняется (свойство распределённого сбора). Документируется.
6. Точное поведение PBS API при `ns` с вложенностью в снимках (`?ns=` — точный
   namespace, вложенные отдельными вызовами) — в коде реализовано и
   протестировано на стенде; на живом PBS не перепроверялось. **[гипотеза]**

## 9. Разбиение реализации на малые шаги

1. `pbs_source`: многомерная карта + обновление контракт-тестов (T10-часть).
2. Чистый селектор `select_pbs_evidence` + unit-тесты T1–T5, T8 (на словарях).
3. `fake_pve`: pbs-ряды `storage_cfg` с server/datastore/namespace; тесты
   харнес-слоя (существующие provider-тесты харнеса не должны сломаться).
4. `collector`: guarded-сбор bindings; изоляция ошибки (T6).
5. `backend/_run`: проводка (многомерная карта → селектор → плоская карта в
   `collect_cluster`); T10.
6. `domain`: поле `pbs_scope` + reason; сборка отчёта.
7. `ui`: caveat + i18n (5 локалей, `_I18N_VERSION` 39→40, `check_release`).
8. Документация: KNOWN LIMITATION → решение; исходный аудит D5 → решён.
9. Полный прогон: `QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest -q -n 3`
   + `.venv/bin/ruff check virtdeck tests`.

Каждый шаг — отдельный коммит, шаги 1–5 не зависят от UI и держат все тесты
зелёными (T10 — инвариант совместимости).
