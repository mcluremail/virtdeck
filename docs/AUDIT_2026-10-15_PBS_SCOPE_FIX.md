# Этап 6.2.3 — исправление D5: изоляция PBS-снимков между кластерами

Дата: 2026-10-15. Базис: `docs/AUDIT_2026-10-15_PBS_SCOPE.md` (аудит 6.2.2, ТЗ фикса),
`docs/AUDIT_2026-10-14_FLEET_BACKUP.md` (D5). Релиз v3.0.5 не затронут; изменения — в `main`.

## 1. Суть дефекта и устранение

D5: карта PBS-снимков строилась один раз на весь флот с ключом `(backup_type, backup_id)`
и применялась ко всем гостям всех кластеров. При совпадении VMID снимок одного кластера
ложно подтверждал актуальность копии гостя другого кластера.

Устранение — двухуровневая схема:

1. **Многомерный сбор** (`fleet/pbs_source.py`): доказательства собираются с сохранением
   источника — `{(server, port, datastore, ns) → {(backup-type, backup-id) → ts}}`.
2. **Скоупинг по привязкам** (`fleet/pbs_scope.py`, новый): каждый кластер получает только
   доказательства тех PBS-хранилищ, на которые ссылаются его собственные pbs-строки
   `GET /storage`. Общей флотовой карты больше не существует ни в одном кодовом пути.

Контракт domain (`build_backup_states`, плоская карта) не менялся — на вход подаётся уже
скоупированная карта (вариант «domain-агрегация» из аудита, A1–A5).

| Шаг аудита | Реализация |

| A2. Привязки | `collector.collect_pbs_bindings` — `provider.cluster.list_storage_configs()` (существующий метод, нового API нет), извлечение чистой функцией `bindings_from_storage_configs` |

| A5. Честные состояния | `ClusterFleetReport.pbs_scope`/`pbs_scope_reasons` + жёлтая строка в UI |

## 3. Принятые решения (документированные)

1. **Неоднозначность — попарно по гостям, не по всему источнику.** Если источник
   `(server, datastore, ns)` разделяют ≥2 кластера и идентификатор `(type, vmid)` есть
   у нескольких из них — доказательства источника по **только этим** идентификаторам
   исключаются у всех кластеров-участников (снимок неатрибутируем). Остальные гости того
   же источника сохраняют подтверждения (безопасно и без неоправданной потери данных).
   Если у гостя, кроме неоднозначного, есть однозначный источник — берётся максимум
   однозначных времен (свежее неатрибутируемое время не может «пробить» чужой кластер).
2. **Единица достоверности — датастор.** Датастор из `collected_stores` даёт
   подтверждённое отсутствие (пустой namespace = пусто, а не «нет данных»); отсутствие
   датастора в collected = недоступность → статус `unavailable`, доказательства других
   источников кластера сохраняются (правило 9).
3. **Нормализация сервера** — `server_key`: strip + lower, порт явный или 8007 по
   умолчанию. FQDN ≠ IP ≠ короткое имя (без DNS и эвристик). Нечисловой порт → ошибка
   привязки, а не молчаливая подмена. Привязки сравниваются с ключом PBS-конфига
   буквально — совпадение `server` в storage.cfg с `host` PBS-конфига VirtDeck остаётся
   на совести конфигурации (см. §7, ограничения).
4. **Статусы** — `ok` / `unavailable` / `ambiguous`. Приоритет: `ambiguous` (потеря
   неатрибутируемых снимков) > `unavailable` (недоступность части данных); причины
   перечисляются полностью в `pbs_scope_reasons` (технические строки на английском —
   тот же паттерн, что у деталей CollectError в D4).
5. **PBS не настроен** (`pbs_cfgs` пуст) → селектор не вызывается, запросов `GET /storage`
   нет, скоуп `ok` без доказательств (PBS-свежесть — просто не часть отчёта).
6. **Сбой `GET /storage`** → `CollectError("pbs_storage_config")` (отчёт incomplete,
   как у других источников) + скоуп `unavailable`: без привязок карта не строится,
   флотовая карта не подставляется как fallback.
7. **Момент селекции** — после барьера всех кластеров цикла: неоднозначность выявляется
   флотово (нужны привязки и гости всех кластеров). `cluster_done` излучается уже после
   селекции (потребителей промежуточного сигнала в UI нет — проверено grep'ом);
   `finished_all` несёт финальные бандлы. Все данные цикла (evidence, привязки, отчёты)
   собраны внутри одного `_run` одного экземпляра воркера — поздние результаты старого
   поколения в новый отчёт не попадают (T13).
8. **Секреты** — полные ряды `GET /storage` (содержат `password`) и PBS-конфиги
   (содержат `token_value`) нигде не логируются; в problem-строках — только id хранилища (T14).

## 7. Ограничения (честные, задокументированные)

- **Повторное использование VMID при общем источнике** (сценарий подтверждён владельцем,
  2026-10-15): гость `vm/101` удалён в кластере A и создан заново в кластере B, оба пишут
  в один `(server, datastore, ns)`. Пересечение идентификаторов проверяется по **текущему**
  составу гостей (правило 8): если 101 остался только у B, доказательства источника
  засчитываются B, и старый снимок A может ложно подтвердить свежесть нового гостя B, пока
  у того нет собственной копии. Из потребляемых метаданных PBS (type/id/time/verify;
  owner-атрибуция признана ненадёжной в аудите 6.2.2) принадлежность невосстановима,
  эвристика не вводится. Средство — конфигурационное: раздельные datastores или namespaces
  на кластер. Поведение зафиксировано тестом
  `test_pbs_scope.py::test_rule8_residual_risk_vmid_reuse_after_deletion`.
- Селектор не различает IP/FQDN/короткое имя одного сервера: если `server` в storage.cfg
  написан иначе, чем `host` в PBS-конфиге VirtDeck, источник считается недоступным
  (статус `unavailable` с причиной — ситуация видимая и диагностируемая, не тихая).
  Принято владельцем (2026-10-15): видимая непроверенность лучше небезопасных DNS-эвристик.
- `cluster_done` излучается после барьера: для больших флотов строки появляются пакетно,
  а не по одному. Потребителей промежуточного сигнала нет — подтверждено повторным grep
  (2026-10-15), принято владельцем как осознанный компромисс.
