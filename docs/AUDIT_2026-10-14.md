## A. Сводка дефектов

### C-1 (P2, подтверждён) — таймаут источника пулов выглядит как подтверждённое отсутствие

- **Файлы:** `fetch.py:92-135` (`fetch_pools`; `pools_failed` ставится
  только в `except`, строка 134), `fetch.py:183-196` (после
  `join_phase1` живость проверяется **только** у res-потока `phase1[2]`),
  `fetch.py:444` (`emitted_pools = None if pools_failed else pools`),
  потребитель `mainwindow.py:1910-1915`.
- **Цепочка:** `pool_api.list()` зависает дольше `join_phase1` → поток
  `fetch_pools` переживает join, `pools_failed=False` (нет исключения) →
  `emitted_pools=[]` → payload `ok` с `pools: []` → `on_worker_finished`:
  `pools_data is not None` → `_pool_repo.remove_host(host)` → пулы хоста
  стёрты. Пейлоад неотличим от подлинного «пулов нет».
- **Последствия (до следующего успешного цикла):**
  1. `_pool_repo` теряет пулы хоста → `CreateVmDialog.pool_combo`
     (`mainwindow.py:655` → `create_vm_dialog.py:258`) пуст — выбрать пул
     нельзя;
  2. `all_pools` пуст; `detail_panel.all_pools` (не читается, см. 🟡);
  3. **standalone:** `vm["pool"]` наполняется только из `vmid_to_pool`
     (`fetch.py:337`) → группировка по пулам в дереве (`tree_panel.py:989-1008`)
     схлопывается; **cluster:** `vm.pool` приходит нативно из
     `/cluster/resources` (`fetch.py:280-282` только дополняет) → группировка
     выживает.
- **Воспроизведение:** `test_r4_pool_thread_timeout_looks_like_confirmed_absence`
  — PASSED (дефект-демонстрация).
- **Кэш:** пулы в ресурсный кэш не пишутся (`save_resources_cache` =
  nodes/vms/storages) — стирание только в памяти, рестартом не
  восстанавливается, но и не портит кэш.

### C-2 (P2, подтверждён; шире прежнего описания) — сбой HA неотличим от «HA-групп нет», плюс вайп начала цикла

**(a) Производитель** — `fetch.py:137-154` (`fetch_ha`): `except Exception:
pass`, флага сбоя нет; `fetch.py:466/478` — `ha_groups` включается в payload
всегда. Потребитель — `mainwindow.py:1923-1924`:
`self.all_ha_groups[host] = [HaGroup.from_pve(g) for g in data.get("ha_groups", [])]`
— безусловная запись.
- Варианты воспроизведения: исключение `list_ha_groups()` → `[]` (репро
  `test_r4b_ha_failure_wipes_ha_groups` — PASSED); **таймаут** потока
  (живость `phase1[1]` не проверяется) → `[]` (новое репро D1 — PASSED).
- Комментарий `mainwindow.py:1922` («same rule» как у ISO) не соответствует
  реализации: omit-правило для HA не реализовано ни в одной из сторон.

**(b) Потребитель, вайп начала цикла** — `mainwindow.py:1605`:
`self.all_ha_groups.clear()` в начале каждого `refresh_data()`. Хосты,
ответившие `error`/`partial`, в `else`-ветке (`1929-1956`) не перезаполняются
→ их HA-группы исчезают на весь цикл. Для пулов тот же приём **убран** в 4.2
(`1627-1632`: «Pools are NOT cleared here… only hosts that left the
configuration are dropped») — HA пропущен асимметрично. Репро
`test_d2_hard_cycle_clears_ha_of_errored_host` — PASSED.

- **Последствия:**
  1. HA-таб хоста (`_host_tabs.py:3547-3578`) рендерит группы **из
     `all_ha_groups`** → пустая таблица «HA Groups» при работающих ресурсах
     (ресурсы тянет свой воркер `HaResourcesWorker` с честным error-путём,
     `ha.py:18-38`) — противоречивая картина;
  2. `_on_vm_ha_add` (`mainwindow.py:1354`) → «No HA groups available» —
     добавить VM в HA нельзя;
  3. `CreateVmDialog.ha_combo` (`create_vm_dialog.py:514`) пуст;
  4. при `error`-хосте данные пропадают даже без сбоя самого HA (путь b).
- **Кэш:** HA не кэшируется — потеря только в памяти, до следующего `ok`
  этого хоста с успешным HA-фетчем.
- **Гейт-совместимость:** оба пути — после identity-гейта
  (`_resolve_result_cfg`, `1871-1873`) и epoch-гейта (`1882-1883`): чужой или
  устаревший результат пулы/HA не трогает. Soft-путь (`soft_refresh`,
  `2142+`) pools/HA не трогает вовсе.

### 🟡 Наблюдения (вне ядра C-1/C-2)

- **partial не различается потребителем:** статус `partial` (4.1) попадает в
  `else`-ветку `on_worker_finished` и обрабатывается как ошибка: нодам
  ставится ERROR-флаг, показывается уведомление «Connection error». Пейлоад
  partial несёт `pools`/`ha_groups`, но `else`-ветка их игнорирует
  (безвредно). Именно из-за этого partial-хост теряет HA через путь (b).
- `fetch_pool_detail`: тихий fallback `p.get("members")` при ошибке detail —
  enrichment `vmid_to_pool` может быть частичным; допустимо (enrichment не
  влияет на достоверность списка), но в standalone даёт `pool=None`.
- `all_pools` (список-агрегат) чистится в начале цикла и перезаполняется
  первой `ok` — короткое окно устаревшего пустого значения (косметика);
  `detail_panel.all_pools` записывается, но нигде не читается (мёртвое поле).
- Поток пулов, переживший join, может дописать `vmid_to_pool` уже после
  эмиссии — на payload не влияет (rebind `pools` создаёт новый список;
  enrichment потреблён до эмиссии).

## B. Карта потока данных

### Pools

```
provider.pools.list() ── thread fetch_pools ──┐
  pool_api.get(pid) ×N (detail, join 10s) ────┤ pools_failed ← только except
                                              ▼
emitted_pools = None if pools_failed else pools          fetch.py:444
  ▼ result_ready.emit{status ok|partial, pools, nodes, vms, storages, …}
  ▼ [identity gate _resolve_result_cfg → None: дроп всего результата]   mw:1871
  ▼ [epoch gate answer_current → устаревший ответ дропается]            mw:1882
  ▼ status=="ok"
pools_data is None → keep previous            ┐
иначе remove_host(host) + add(DomainPool)     ┘ mw:1910-1915
  ▼
_pool_repo (identity (host, poolid)) → all_pools = _pool_repo.all()
  ▼
CreateVmDialog.pool_combo (for_host, mw:655) · detail_panel.all_pools (не читается)
Дерево: vm.pool ← /cluster/resources (нативно) ∪ vmid_to_pool (standalone — только он)
Кэш: не хранится. Soft-refresh: не трогает.
```

### HA

```
cluster_api.list_ha_groups() ── thread fetch_ha ── except: pass   НЕТ флага
ha_groups: [dict] | []   (в payload всегда, даже при сбое)        fetch.py:466/478
  ▼ [identity gate] → [epoch gate]                                mw:1871/1882
  ▼ status=="ok" (else-ветка HA не трогает)
all_ha_groups[host] = [HaGroup…from_pve(g) for g in data.get("ha_groups", [])]
                                                    безусловно    mw:1923-1924
  ▲ refresh_data(): all_ha_groups.clear() — error/partial-хосты не
    перезаполняются                                                mw:1605
Потребители:
  HA-таб: группы ← all_ha_groups (все хосты); ресурсы ← HaResourcesWorker
          (свой error-путь, ha.py:18-38)                _host_tabs:3547-3583
```

Три состояния запроса фактически различаются только для пулов и только на
ветке «исключение»: подтверждённое отсутствие (`[]`), данные (`[...]`),
«не получено» (`None`). Для HA второе и третье неотличимы; таймаут любого
optional-источника неотличим от первого.

## C. Предлагаемое исправление (минимальное, реализацию не начинаем)

Обязательные (точки изменения):

1. **`fetch.py`, после `join_phase1`** (зеркало проверки res-потока
   `191-196`):
   - `phase1[0].is_alive()` → `pools_failed = True` (таймаут пулов = «не
     получено», как и исключение);
   - `phase1[1].is_alive()` → новый флаг `ha_failed = True`.
2. **`fetch.py` `fetch_ha`**: `except Exception:` → `ha_failed = True`
   (вместо `pass`), лог как у пулов.
3. **`fetch.py` эмиссия**: `ha_groups` включать в payload только при успехе
   (`emitted_ha = None if ha_failed else ha_groups`; ключ включать как для
   пулов — `None`-сентинел). Частичный/ok-пейлоады — оба.
4. **`mainwindow.py` ok-ветка**: `ha_data = data.get("ha_groups")`;
   `if ha_data is not None: all_ha_groups[host] = [...]` — зеркально пулам.
5. **`mainwindow.py` `refresh_data`**: убрать `all_ha_groups.clear()`
   (1605); добавить дроп записей ушедших из конфигурации хостов (зеркало
   блока пулов `1630-1632`).

Итог: все optional-источники следуют одной конвенции — «ключ есть =
подтверждённые данные (включая пустые), ключа нет/None = не получено,
предыдущие данные сохраняются». Новый глобальный механизм не вводится;
существующие гейты (identity, epoch, поколение) применяются к pools/HA
автоматически, поскольку те едут в том же payload.

Необязательные улучшения:

6. HA-таб: явный маркер «данные HA не получены» для хостов без ключа
   (сейчас пустая таблица неотличима от «групп нет»); требует i18n.
7. Отдельная ветка `partial` в `on_worker_finished` (сейчас else=error):
   не разменивать ERROR-флаги на «Connection error»-уведомление. Отдельная
   задача — фикс (5) снимает главный ущерб.
8. Удалить мёртвое `detail_panel.all_pools` или начать читать.

Риски предложенного: хост, не ответивший `ok`, дольше хранит старые пулы/HA —
это и есть цель (симметрично пулам с 4.2); подтверждённое отсутствие
по-прежнему чистит данные в тот же цикл.

## E. Риски и вопросы владельцу

1. **Семантика сентинела для HA:** расширить конвенцию пулов (None/omit =
   «не получено», [] = подтверждённое отсутствие) — предложение C-1..4.
   Альтернатива — omit ключа вместо None (менее единообразно, но меньше
   шума в payload). Требуется выбор.
2. **Кэширование pools/HA:** сейчас не хранятся — после рестарта пусто до
   первого успешного цикла. Расширять ресурный кэш (и его conn_id-контракт)
   в 6.1 не предлагаю; фиксировать как известное ограничение?
3. **partial в потребителе:** сейчас обрабатывается как error (ERROR-флаги +
   «Connection error»). Чинить в 6.1 (п. C-8) или отдельным этапом?
4. **HA-таб UX:** отдельный маркер «не получено» на уровне хоста (C-6)?
5. **Глубина чистки `all_ha_groups` при неоднозначных (ambiguous) хостах:**
   они исключены из refresh — при (5) их старые HA-данные сохранятся, что
   согласуется с поведением пулов и штубов нод.
