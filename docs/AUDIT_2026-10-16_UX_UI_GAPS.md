# Аудит полноты UX/UI-аудита VirtDeck (GAPS, 2026-10-16)

Дополнение к [AUDIT_2026-10-16_UX_UI.md](AUDIT_2026-10-16_UX_UI.md) (серия UX-0…UX-8).
Задача этого документа — не повторять основной аудит, а проверить его полноту:
систематические пробелы охвата, сценариев, методики и доказательств.
Код приложения не менялся; все проверки — чтение кода и offscreen-прогоны.

Категории находок: **[дефект]** подтверждено, **[гипотеза]** требует
воспроизведения, **[покрытие]** недостаток проверки аудита, **[продукт]**
отсутствующая функция/ограничение.

## 5.1. Резюме полноты аудита

**Основной аудит покрывает хорошо:**

- Картографию поверхностей (26) и матрицу действий (44 спеки × меню/палитра,
  runtime-дамп) — UX-0/UX-4.
- Дизайн-систему и темы (токены, перекраска, QSS) — UX-1/UX-2.
- Одиночные loading/error/empty-состояния 9 поверхностей — UX-3.
- Формы и диалоги (2 глубоких разбора + скан ~20) — UX-5.
- i18n-механику (словари, локали, RTL-структура) — UX-6.
- Клавиатуру/фокус/цели нажатия/DPR — UX-7, с runtime-доказательствами.

**Действительно за рамками:**

- Сквозные рабочие сценарии (A): «действие → задача → результат»,
  «проблема Fleet Health → объект → диагностика» не воспроизведены ни разу
  как непрерывные цепочки.
- Комбинации состояний (H): только одиночные состояния; частичные отказы,
  исчезновение объектов, смена режима во время загрузки — не тестировались.
- Поведенческая проверка PBS (F): здоровые состояния датасторов не
  отрендерены ни разу; restore/verify существуют в коде, но не проверены.
- Масштабирование парка (B): практических измерений нет; фикстуры — 2-3
  хоста и 3 VM.
- Масштабирование системным шрифтом (G/I): не проверялось — и не работает
  (GAP-2).

**Ограничения методики, влияющие на уверенность:**

1. Все рендеры — на синтетических фикстурах (2-3 хоста, 3 VM, 1 storage);
   воркеры подавлены (`tests/ui/runtime_contract.py`) — асинхронная часть
   (задачи, UPID, прогресс) в кадры не попадала.
2. Live-проход ограничен инфраструктурой (1 хост, 7 VM; PBS-логин за
   firewall) — здоровые PBS-состояния и полный парк не видны.
3. Артефакты-доказательства (кадры, дампы, скрипты) лежат в
   `/tmp/opencode/ux_audit/` — вне репозитория и вне версионирования
   (GAP-1): ссылки основного отчёта на эти файлы с течением времени
   становятся невоспроизводимыми.
4. Скринридеры/реальные AT не проверялись — только Qt-механика
   (AccessibleName, focus chain).

## 5.3. Новые находки

### GAP-1. Доказательства аудита не версионируются — [покрытие], P2

- **Факт.** Все кадры, дампы и скрипты основного аудита лежат в
  `/tmp/opencode/ux_audit/` (ux0…ux7): ссылки вида «кадр
  `light.hosts_no_selection.png`» указывают на временную директорию.
- **Сценарий.** Через месяц по отчёту невозможно отличить проверенный факт
  от заявления: артефакт исчез вместе с /tmp.
- **Последствия.** Достоверность отчёта деградирует; спорные находки
  нельзя перепроверить.
- **Почему не покрыто.** Основной аудит фиксирует артефакты, но не их
  долговечность.
- **Рекомендация.** Выборочные ключевые кадры (по 2-3 на этап) — в
  `docs/assets/ux_audit/`; рендер-скрипты — в `tests/audit_render/` (они
  самодостаточны и используют `tests/ui/runtime_contract.py`).
- **Критерий приёмки.** Из чистого клона репозитория каждый кадр отчёта
  можно воспроизвести командой из документации.

### GAP-2. Интерфейс не масштабируется системным шрифтом — [дефект], P2

- **Факт.** Универсальное QSS-правило `* { font-size: 14px; … }`
  (`theme.py:258-262`) плюс точечные 10-13px правила пинают все кегли.
  Установка шрифта приложения 12pt (при базовом 9pt) **не меняет отрисовку**:
  рендер Create VM при 12pt идентичен 9pt (`/tmp/opencode/ux_audit/gaps/
  bigfont_create_vm.png`; код прогона `gaps_font.py`). DPR-масштабирование
  (QT_SCALE_FACTOR) при этом работает — проверено в UX-7.
- **Сценарий.** Пользователь со слабым зрением увеличивает системный шрифт
  (GNOME/KDE/Qt-тема) — VirtDeck остаётся в 14px; текст 10-11px (U38)
  нечитаем, обходного пути внутри приложения нет.
- **Последствия.** WCAG 1.4.4 (Resize Text) фактически не выполняется;
  доступность падает для всей категории пользователей.
- **Почему не покрыто.** UX-7 проверял DPR (пиксельную плотность), но не
  шрифт-скейлинг; U38/A6 — про малые кегли и отсутствие шкалы-токенов, не
  про неработающий механизм масштабирования.
- **Рекомендация.** Перевести базовую шкалу с px на относительные
  единицы (rem-подобный расчёт от `QFontMetrics`/app font) — пакет работ
  вместе с A6 (токены шкалы). Короткий вариант: масштабный коэффициент при
  сборе QSS (`int(14 * k)`), k из настройки.
- **Критерий приёмки.** Рендер при font 12pt показывает пропорционально
  увеличенный UI без обрезок в диалогах; автотест сравнивает высоту
  строки при 9pt и 12pt.

### GAP-3. Сквозной жизненный цикл «действие → задача → результат» не воспроизводился — [покрытие], P1

- **Факт.** Во всех рендер-прогонах основного аудита воркеры подавлены
  (`install_fake_pool`/`install_guard`); строка задачи в доке ни разу не
  появилась как результат реального запуска действия в той же сессии.
  Код-путь существует: `_on_vm_action_from_tree` (`mainwindow.py:996-1032`):
  confirm → optimistic-статус → `VmActionWorker` → `action_result` →
  `refresh_data()`.
- **Сценарий.** Администратор запускает Start VM: обязан видеть (1) смену
  статуса в дереве, (2) строку задачи с UPID, (3) финальный статус, (4)
  обновление состояния VM. Разрывы любого звена (задача не появилась,
  статус «завис», refresh не пришёл) не были бы замечены текущей методикой.
- **Последствия.** Ключевой операционный цикл инфраструктурного клиента
  не имеет ни одного поведенческого доказательства в отчёте.
- **Почему не покрыто.** Методика подавляла асинхронность ради
  детерминированных кадров — осознанный trade-off, но он оставил цикл
  без покрытия.
- **Рекомендация.** Runtime-сценарий: fake API с отложенным ответом
  (UPID → running task → exitstatus) + авто-fire действия; проверки:
  появление строки, optimistic→confirm, финальный refresh. Место —
  `tests/ui/` рядом с `runtime_contract.py`.
- **Критерий приёмки.** Тест проходит: строка задачи появилась, статус
  сменился, после завершения состояние VM соответствует результату.

### GAP-4. Маркировка свежести данных — голое время в статус-баре — [дефект], P2

- **Факт.** Свежесть данных помечена только добавлением
  `now_str = datetime.now().strftime("%H:%M:%S")` в конец строки статус-бара
  (`mainwindow.py:2478, 2508`) — без подписи «updated» рядом с
  «Hosts: … VMs: … CPU: …». Карточки, detail-панели, PBS, Fleet Health
  свежесть не показывают вовсе; есть только `Offline (cached)` для
  офлайн-режима (`:2507`).
- **Сценарий.** Хост отключился от сети в 10:00; в 10:40 оператор смотрит
  карточку с метриками 10:00 — значения выглядят актуальными; время в
  статус-баре без подписи читается как «текущее время».
- **Последствия.** Оператор принимает устаревшие данные за актуальные —
  ровно тот класс заблуждений, который для инфраструктурного инструмента
  дороже любого косметического дефекта.
- **Почему не покрыто.** U8 нашёл отсутствие дедлайна воркера (механика
  обновления); L3 — двусмысленность знаменателей; отображение свежести как
  свойство поверхностей не проверялось.
- **Рекомендация.** Подписать время («Updated 10:00:12»), показывать
  per-surface возраст данных (например, в заголовке карточки хоста — время
  последнего успешного опроса этого хоста), при провале обновления —
  сохранять прежний штамп и подсвечивать.
- **Критерий приёмки.** На каждом состоянии (свежие/устаревшие/частичные
  данные) возраст данных читается без чтения документации.
- **Гипотеза для проверки:** обновляется ли штамп при частичном провале
  (один хост из трёх не ответил) — определяет, маркирует ли текущее время
  «смешанное» состояние.

### GAP-5. Комбинации состояний не тестировались — [покрытие], P2

- **Факт.** UX-3 покрывает одиночные состояния 9 поверхностей. Комбинации —
  часть кластера доступна, объект исчез между обновлениями, смена режима
  дерева при идущей загрузке, повторный запрос после ошибки, пустой
  результат при успехе — не воспроизводились. Механизм восстановления
  выделения при rebuild существует (`find_item_by_key`,
  `tree_panel.py:1418+`; runtime-проверка: currentItem «web-01» сохраняется
  при полном rebuild) — но поведение при исчезновении выделенного объекта
  не проверено.
- **Сценарий.** Оператор держит выделенной VM, которую удалили с другого
  клиента; после refresh выделение… (гипотезы: сбрасывается на первый
  элемент через `select_first_item`, остаётся на несуществующем ключе,
  detail показывает последнюю копию данных).
- **Последствия.** Тупиковые/противоречивые состояния после штатных
  операций парка не имеют документированного поведения.
- **Почему не покрыто.** Матрица UX-3 строилась по типам состояний, не по
  переходам; фикстуры не эволюционировали между populate-ами.
- **Рекомендация.** Матрица переходов (состояние × событие: refresh-ok,
  refresh-fail, объект исчез, объект появился) поверх существующего
  рендер-харнесса — данные мутируют между populate-ами.
- **Критерий приёмки.** Для каждой комбинации зафиксировано ожидаемое
  поведение дерева/детали/сводки; расхождения — отдельными находками.

### GAP-6. Повторное нажатие во время выполняющейся операции — [гипотеза], P3

- **Факт.** `_on_vm_action_from_tree` (`mainwindow.py:996-1032`) не
  блокирует повторный запуск: меню/палитра остаются активными, пока задача
  в полёте. Есть optimistic-статус и rollback (включая pool-full,
  аудит 6.3.2a D6) — но защита от двойного клика не обнаружена в коде.
- **Сценарий.** Start VM «залипает» на 5 с — оператор жмёт ещё раз; второй
  worker уходит в PVE, задача завершается ошибкой («already running»),
  появляется непонятная ошибка на штатное действие.
- **Последствия.** Ложные ошибки при нормальной работе; нагрузка на API.
  Оценка смягчена тем, что PVE сам отвергает дубль.
- **Почему не покрыто.** UX-4 проверял доступность действий по состоянию
  selection, но не по состоянию «операция уже идёт»; runtime-прогоны с
  реальной задержкой не выполнялись.
- **Рекомендация.** Проверка-воспроизведение: fake API с задержкой 2 с,
  двойной вызов действия; фиксировать поведение. Если подтвердится —
  дизейбл пункта на время полёта (по optimistic-ключу).
- **Критерий приёмки.** Двойной клик не создаёт вторую задачу; интерфейс
  объясняет, что операция уже выполняется.

### GAP-7. Масштабирование парка: измерений нет; у дерева нет фильтра — [покрытие] + [продукт], P2

- **Факт.** Фикстуры всех рендеров — 2-3 хоста, 3 VM, 1 storage.
  `_build_tree` полностью пересобирает дерево на каждое обновление
  (`update_data` → `_build_tree`, `tree_panel.py:736-753`); стоимость
  rebuild при 200+ VM не измерялась. Поиск по дереву отсутствует: поле
  «Filter...» относится к доку задач (`cluster_tasks_widget.py:176`);
  глобальный поиск (Ctrl+F) покрывает обнаружение, но не фильтрацию дерева
  на время работы. Имя VM в дереве — без VMID и ноды
  (`_add_vm_item`, `tree_panel.py:895-898`) — различимость одинаковых имён
  упирается в U1 (атрибуция) и не тестировалась на мульти-подключениях.
- **Сценарий.** Парк 5 кластеров × 10 узлов × 40 VM: поиск «нужной VM»,
  скорость обновления дерева, поведение при частично недоступном парке.
- **Последствия.** Приложение заявлено для централизованного управления;
  пригодность на реальном масштабе не подтверждена ни измерением, ни
  сценарием.
- **Почему не покрыто.** Основной аудит не ставил целью производительность;
  малые фикстуры выбраны для детерминизма кадров.
- **Рекомендация.** Профиль нагрузки: 5 подключений, 20 хостов, 200 VM,
  50 задач; замеры: время `_build_tree`, latency обновления, память.
  Поведенческий тест: два VM с одинаковым именем на разных узлах — поиск,
  выделение, detail (правильный ли объект открыт).
- **Критерий приёмки.** При профиле 200 VM обновление дерева ≤200 мс на
  референс-машине; различение имён возможно без открытия detail.

### GAP-8. PBS-путь не проверен поведенчески (restore/verify/снимки) — [покрытие], P1

- **Факт.** Функциональность существует: снимки VM и rollback
  (`_vm_tabs.py:167`), Restore (`:210-213`, `on_vm_restore`), датастор-панель
  с `show_datastore` (`pbs_panel.py:298`); но здоровые PBS-состояния не
  отрендерены ни разу (датастор-вкладки Status/Snapshots/Jobs пусты во всех
  кадрах основного отчёта — признано ограничением в UX-3/UX-6), restore/verify
  флоу не запускались даже на fake-данных.
- **Сценарий.** «Найти последнюю копию VM → проверить её → восстановить
  файл/VM» — центральный сценарий продукта с PBS; в отчёте нет ни одного
  кадра этого пути.
- **Последствия.** Наибольший непокрытый сценарий аудита; дефекты здесь
  (неразличимость verify/restore, потеря привязки копия→VM) обнаружатся
  только у пользователей.
- **Почему не покрыто.** Ограничение среды: PBS-логин за firewall, воркеры
  подавлены — метод прямого `show_datastore`+fill описан в отчёте как
  решение, но применён не был.
- **Рекомендация.** (1) Оффлайн-сессия с заполненной PBS-панелью (fake
  данные: датасторы, снимки, задачи) — рендер-матрица состояний; (2)
  поведенческий прогон restore/verify на тестовом PBS по санкции владельца.
- **Критерий приёмки.** Кадры Status/Snapshots/Jobs с данными; сценарий
  restore проходит до экрана подтверждения (без реального запуска).

### GAP-9. Даты и время не локализованы — [дефект], P3

- **Факт.** Все даты — жёсткий `strftime`: `%Y-%m-%d %H:%M:%S`
  (`_vm_tabs.py:1062`, `_host_tabs.py:1424`), `%H:%M` (fleet_health:505-506),
  `%H:%M:%S` (статус-бар). QLocale не используется.
- **Сценарий.** Пользователь ru-локали видит «2026-10-16 14:03» — ISO-формат
  консистентен и понимаем; локализованный формат отсутствует как выбор.
- **Последствия.** Минимальные; консистентность ISO — защитимый
  дизайн-выбор, но он нигде не зафиксирован как осознанный.
- **Почему не покрыто.** UX-6 проверял строки-переводы, а не форматы
  дат/чисел.
- **Рекомендация.** Зафиксировать решение: либо QLocale-форматирование,
  либо ISO-формат как заявленный стандарт в docs/THEMES.md.
- **Критерий приёмки.** Правило форматирования дат описано и соблюдено
  всеми поверхностями.

### GAP-10. Причина недоступности действия не сообщается — [дефект], P2

- **Факт.** Ни один spec не несёт причины disabled (`action_specs.py` —
  поля `enabled`/`scopes` есть, поля reason нет). Палитра скрывает
  недоступные действия, меню показывает серым без пояснения (UX-4).
- **Сценарий.** Оператор видит серый «Migrate» у остановленной VM — почему?
  (нет прав? не тот статус? нет target?). Ответа нет ни в меню, ни в
  tooltip, ни в статус-баре.
- **Последствия.** Пользователь не может отличить «мне нельзя» от
  «приложение считает по-другому» — прямой путь к поддержке/обходам.
- **Почему не покрыто.** UX-4/UX-8 фиксировали скрытие/серость (U13, U14),
  но не отсутствие объяснения как механизм.
- **Рекомендация.** Опциональное поле `disabled_reason` в spec + tooltip
  на серых пунктах меню; в палитре — показ с причиной вместо скрытия
  (решение владельца).
- **Критерий приёмки.** Для каждого серого пункта меню причина читается.

### GAP-11. Из строки задачи нет перехода к объекту — [продукт], P3

- **Факт.** В доке задач колонки Start/End/Host/User/Description/Status
  (`cluster_tasks_widget.py:129`); клик/двойной клик по строке не
  обрабатывается (grep `itemClicked|itemDoubleClicked` — пусто) — навигации
  к затронутому объекту нет. Для VM-задач целевой VMID живёт только внутри
  Description (текст от API).
- **Сценарий.** Оператор видит красную строку «qmigrate … failed» — чтобы
  найти VM, нужен ручной поиск по имени из Description.
- **Последствия.** Лишние шаги в диагностике; сценарий «обнаружил ошибку →
  открыл объект» не закрыт.
- **Почему не покрыто.** UX-2/UX-8 фиксировали усечение колонок (A9) и
  пустой док (U12); навигация из задачи не рассматривалась.
- **Рекомендация.** Двойной клик по задаче → выбор объекта в дереве
  (по host/vmid из задачи, если тип распознан).
- **Критерий приёмки.** Двойной клик по задаче VM открывает эту VM.

## 5.4. Недостающие сценарии приёмки (по убыванию риска/ценности)

1. **Операционный цикл**: выбор VM → Start → строка задачи с UPID →
   optimistic-статус в дереве → завершение → финальный статус и
   обновлённые метрики; затем Stop → повторный запуск во время полёта
   (GAP-3, GAP-6).
2. **Частичный отказ**: 3 подключения, одно с SSL-ошибкой → сводка, дерево,
   счётчики, статус-бар; восстановление связи → повторное обновление →
   все поверхности согласованы (GAP-4, GAP-5).
3. **PBS-путь**: подключение PBS → датастор с данными → вкладки
   Status/Snapshots/Jobs → привязка копии к VM → экраны verify и restore
   до подтверждения (GAP-8).
4. **Масштаб**: 5 подключений / 20 хостов / 200 VM → время обновления
   дерева, поиск VM по имени при дубликатах, скролл таблиц задач (GAP-7).
5. **Keyboard-only полное подключение**: Add Server → Create VM →
   удаление VM — без мыши, с видимым фокусом (U34/U35 после фиксов).
6. **Смена темы/языка/масштаба**: после каждой смены — без повторного
   получения данных; состояние дерева, выделение, детали сохраняются
   (A7-регресс, U31, GAP-2).

## 5.6. Что не нужно делать

- Переписывать дерево или дизайн-систему: находки U1/U9 решаются точечно;
  фундамент (токены, реестр действий, optimistic-статусы) здоров.
- Добавлять подтверждения на все операции без разбора: у деструктивных
  подтверждения уже есть и хорошо сделаны (чекбокс Delete VM, текстовый
  confirm удаления хоста/кластера); риск — в повторном нажатии и
  маркировке свежести, не в отсутствии «Are you sure».
- Заявлять WCAG-соответствие: методики сертификационных проверок
  (скринридеры, профиль пользователей) в аудите не было.
- Чинить терминологию до решения владельца о каноне (хост/узел, ВМ/VM,
  датастор) — иначе U25/U27/U28 вернутся.
- Гнаться за 100% покрытием локалями fr/es рендерами: риски там
  малы (проверено длинами строк), цена высока.
- Оптимизировать производительность до измерений (GAP-7): повода нет,
  есть только отсутствие данных.
