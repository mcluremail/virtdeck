## 2. Подтверждённое поведение до исправления

- **D10.** При отсутствии прав на чтение verify/prune-job'ов таблица заданий
  показывала только sync (или пусто) без какого-либо указания, что часть
  источников недоступна: «заданий нет» вместо «не прочитано».
- **D11.** `login()` при HTTP 200 с не-JSON телом (прозрачный прокси,
  каптизирующий шлюз) поднимал сырой `ValueError`; воркеры ловили его как
  `Exception` и показывали необработанный текст. Валидный JSON, не
  являющийся объектом (список), давал бы `AttributeError` — та же дыра.
  Пустой JSON-объект корректно превращался в «no ticket», но теста не было.
- **D12.** На PVE7 таймаут создания/изменения/удаления задания доходил до
  пользователя как обычная ошибка без подсказки «исход неизвестен»,
  хотя на PVE8+ подсказка была (механизм `_raise_ambiguous` из 6.3.1 D3).
- **D17.** Пустой/битый ответ `/cluster/nextid` → `ValueError/TypeError`
  вне иерархии `ProxmoxError`; воркеры (`except Exception`) показали бы
  сырой текст вместо контролируемого сообщения. Механика подтверждена
  кодом; частота — крайний случай (аудит).
- **D16.** Подтверждено кодом: пустой UPID от дефектного ответа трактуется
  как успех; исход задания PBS в VirtDeck не виден вовсе.

## 3. Изменения по дефектам

### D10 — `PbsProvider.jobs()` → `(jobs, failed_kinds)`, полный отказ — ошибка

**Файлы:** `virtdeck/pbs/provider.py`, `virtdeck/ui/pbs_panel.py`,
`virtdeck/ui/i18n/{ru,ar,zh,fr,es}.json` (1 новый ключ),
`virtdeck/ui/i18n/__init__.py` (`_I18N_VERSION` 42→43).

- Контракт: `jobs() -> tuple[list[PbsJob], list[str]]` — `(задания,
  непрочитанные виды)`. Три состояния ТЗ различены:
  1) успех и действительно пусто → `([], [])`;
  2) частичный результат → `(прочитанные, ["verify", …])`;
  3) список получить не удалось (все три вида) → `PbsError("could not
  read jobs (sync, verify, prune): …")` — ошибка идёт существующим путём
  воркера в `_on_worker_failed`, не маскируясь под пустой список.
  Существующая модель ошибок (`PbsError`) переиспользована, параллельной
  системы статусов нет (по образцу `failed_stores` из 6.2.3).
- UI: `_on_worker_done(kind="jobs")` распаковывает кортеж;
  `_fill_jobs(jobs, failed_kinds)` при частичном результате показывает в
  статус-строке `tr("Some job types could not be read: {kinds}")`
  (`Color.WARNING`); при полном успехе заметка снимается — но только если
  статус-строка до сих пор показывает именно её (не затирает «Job started»
  и ошибки других операций). Пустой успешный результат остаётся «заданий
  нет» без ошибок. Устаревший ответ чужого сервера по-прежнему
  отфильтровывается тегом.

**Новые потребители контракта найдены и обновлены:** единственный
потребитель — `pbs_panel` (через generic `PbsApiWorker`, method="jobs");
других вызовов `.jobs()` в кодовой базе нет (проверено grep'ом).

### D11 — `PbsClient.login()`: разбор ответа внутри контракта ошибок

**Файлы:** `virtdeck/pbs/client.py`.

- `resp.json()` при HTTP 200 обёрнут: `ValueError` →
  `PbsError("PBS auth failed: unparseable response (HTTP {code})",
  status_code)`. Валидный JSON, не являющийся объектом, тоже
  контролируемо превращается в `PbsError` (проверка `isinstance(payload, dict)`).
  Перехватываются **только** ожидаемые ошибки разбора/обработки ответа —
  ошибки программирования не маскируются.
- Диагностика: операция (auth), HTTP-статус; сырое тело и текст исключения
  разбора **не включаются** (тело может содержать секреты) — сообщение
  статично.
- Кейс «200 без тикета» покрыт тестом (`test_login_empty_body_is_controlled_no_ticket`).

### D12 — legacy `/cluster/backup`: симметричный «исход неизвестен»

**Файлы:** `virtdeck/provider/_cluster.py`.

- Три legacy-ветки (create/update/delete, `pve_major<8`) обёрнуты
  `except ProxmoxTimeoutError: self._raise_ambiguous(exc, …)` — ровно как
  ветки `/cluster/jobs`. Тип исключения сохраняется (`ProxmoxTimeoutError`,
  т.е. типизированная иерархия не теряется), сообщение дополняется явной
  подсказкой: «…; job creation may still have been applied on the server —
  refresh the job list to verify».
- Полный путь проверен: провайдер → `ClusterJobCreate/Update/DeleteWorker`
  (без повторов запроса; `_sanitize_error`) → сигнал `error(str)` → тост
  `Job error: {err}` (ключ D15). Различие «ошибка» vs «неизвестный исход»
  сохраняется на всём стеке: типизированное исключение в провайдере,
  единственный вызов (call_count==1 в тестах), подсказка о проверке списка
  вместо автоматического повтора — то же соглашение, что принято в 6.3.1
  для PVE8+-пути. Повторная безмодифицирующая проверка (перечитать список
  заданий) уже доступна пользователю через UI и предлагается подсказкой;
  автоматическую верификацию не добавлял (ТЗ §5.6 — без широкой переработки).

### D17 — `next_vmid()` внутри типизированной иерархии

**Файлы:** `virtdeck/provider/_cluster.py`.

- Конвертация обёрнута: `TypeError/ValueError` →
  `ProxmoxApiError("unexpected /cluster/nextid response: {result!r}")`
  (`from exc`). Молчаливое превращение ошибочного ответа в валидный id
  исключено тестом (`test_next_vmid_error_does_not_produce_an_id`).
- Семантика и вызывающий код не менялись: потребители
  (`backend/vmops.py` ×4, `backend/core.py` retry-хелпер) получают либо
  int, либо `ProxmoxApiError` — оба уже обрабатываются существующими
  путями (воркеры показывают `str(e)`; retry-хелпер пробрасывает ошибку,
  не подставляя идентификатор). Успешные пути (строка/число/дикт)
  сохранены и покрыты тестами (включая предсуществующие).

## 7. D16 — исследование (без реализации)

### Как устроено сейчас

- **Запуск PBS-операций:** `pbs_panel` — «Run now» для sync/verify/prune
  (`_start("run", kind, job_id)`) и «Verify» датастора
  (`_start("verify_datastore", store)`); generic `PbsApiWorker` →
  `PbsClient.run_job` / `verify_datastore` →
  `POST /admin/{kind}/{id}/run`, `POST /admin/datastore/{store}/verify`.
  Ответ PBS содержит UPID-строку; клиент возвращает `self.post(...) or ""`.
- **Обработка результата:** `pbs_panel` показывает «Job started» /
  «Verify started...» (i18n-ключи) без проверки UPID и без запуска
  наблюдения (строки 350–352, 467). UPID не сохраняется: grep по
  `upid` в PBS-части проекта потребителей не находит. Исход задания
  (успех/ошибка PBS) пользователю недоступен. «Забыть снапшот»
  (`forget_snapshot`) — синхронное удаление, задание не создаёт.
- **Готовый механизм поллинга есть только для PVE:**
  `provider/_tasks.py::TaskAPI.get_status/poll` — таксономия исходов:
  `stopped` + `exitstatus` («OK» = успех, иное = собственная ошибка
  задачи), `timeout` (клиентский дедлайн — задача в PVE могла продолжать
  работать), `poll_failed` (состояние нечитаемо — исход неизвестен) с
  бюджетом переносимых последовательных сбоев чтения. Используется
  `backend/core.py` (ожидание завершения PVE-задач с честным различением
  «провал задачи» / «неизвестно» / «не дождались»). PVE-таски также
  показываются в UI списком (`ClusterTasksWorker`, вкладка задач).
  У PBS-клиента эндпоинтов задач нет; `PbsClient.nodes()` (GET /nodes)
  уже есть.

### Ответы на вопросы ТЗ

- **Где и как запускаются операции PBS, требующие отслеживания:**
  `pbs_panel` (run job, verify datastore) через `PbsApiWorker`; результат
  — UPID, который сейчас отбрасывается.
- **Возвращает ли API идентификатор задачи:** да, UPID — для `run` и
  `verify` (`data` = "UPID:…"). Случаи без UPID: деградированный 200
  (data:null/не-JSON) — сейчас даёт пустую строку и ложное «запущено»
  (это и есть дефект D16); отказ (4xx/5xx/таймаут) поднимает `PbsError`
  до UI.
- **Готовый механизм, который можно переиспользовать:** контрактная
  схема `TaskAPI.poll` (такосномия исходов и бюджет сбоев) — переносима
  на PBS почти один в один; сам класс привязан к PVE-сессии proxmoxer,
  для PBS нужен параллельный метод на `PbsClient`/`PbsProvider`, а не
  общий код (разные HTTP-клиенты). UI-паттерны наблюдения за фоном —
  свои: `PbsApiWorker` + пер-инстансные сигналы + `finished→discard`
  + лимит (6.3.2a D9).
- **API-точки, права, состояния (по документации PBS —
  «Подтверждено доступной документацией»; права — гипотеза, проверить на
  стенде):** `GET /nodes/{node}/tasks/{upid}/status`
  (`status: running|stopped`, `endtime`, `exitcode`), `GET
  /nodes/{node}/tasks/{upid}` (полная сводка), `GET
  /nodes/{node}/tasks/{upid}/log` (лог). `node` — имя PBS-сервера,
  берётся из `GET /nodes` (обычно одна запись). Права: токен, запустивший
  задание, читает статус своего задания; чтение чужих задач требует
  более широких прав — уточнить на тестовом стенде.
- **Различение исходов:** `running` → продолжаем наблюдение; `stopped` +
  успех → подтверждённый успех; `stopped` + ошибка → подтверждённый отказ
  (текст ошибки PBS, санитизированный); сбой чтения статуса →
  **неизвестный исход** (не «провал»); клиентский дедлайн → «всё ещё
  выполняется» (тоже неизвестный исход). Категорически не превращать
  «не удалось прочитать статус» в «задание провалилось».
- **GUI и ограничение работников:** поллер — QRunnable с
  пер-инстансными сигналами и `finished→discard` (механика D9), один
  поллер на активный UPID, общий жёсткий лимит одновременных поллеров
  (аналог `_MAX_PBS_WORKERS`), превышение — честный тост. Никаких
  блокирующих циклов в GUI-потоке; шаг опроса — короткий запрос статуса
  с паузой внутри воркера (sleep в воркере допустим, в тестах — нет:
  дедлайны и интервалы инъекцией).
- **Жизненный цикл:** закрытие панели — виджет уничтожается, обработчики
  отключаются, воркер доигрывает в «пустоту» (уже безопасно после D9);
  смена сервера — теги с идентификатором сервера (как у jobs/snapshots);
  таймаут — дедлайн поллера с честным «всё ещё выполняется»; повторное
  открытие — состояния задач не персистятся, показывать «исход
  неизвестен до следующей проверки» либо перечитывать активные задачи.
- **Проверки на заглушках:** полностью покрываемо — фейковый
  `PbsClient` со сценариями (UPID → running → stopped/OK; → stopped +
  ошибка; → сбой чтения; → дедлайн), управляемое «время» через
  инъекцию часов/интервалов, `qtbot.waitSignal`; реальные сети не нужны.

### Минимальный план реализации (решение — отдельно, НЕ реализовано)

1. **Подэтап A (корректность, малый):** честный UPID — `run_job`/
   `verify_datastore` различают «UPID получен» и «ответ неразборчив —
   исход неизвестен» (`data:null` → `PbsError` или явный статус); тост
   в `pbs_panel` без ложного «запущено». Файлы: `pbs/client.py`,
   `ui/pbs_panel.py`, i18n; тесты: деградированный 200, нормальный
   UPID, отказ. Оценка: ~0.5 дня, риск низкий.
2. **Подэтап B (статус задачи):** `PbsClient.task_status(node, upid)`
   (+резолв node через существующий `nodes()`), `PbsProvider.task_status`,
   таксономия исходов по образцу `TaskAPI.poll`. Файлы: `pbs/client.py`,
