### Выбор гостей (D1, A2)

| Сценарий | До | После |

## 4. Round-trip-тесты

Серверная семантика PVE реализована в тестовом стенде
`tests/harness/fake_pve.py`: POST/PUT/DELETE для `/cluster/backup` и
`/cluster/jobs`, валидация pve-vmid-list (слово «all» отвергается),
взаимоисключающие ключи выбора (отправка `vmid` удаляет
`pool`/`all`/`exclude` и т. д.), параметр `delete`, ошибка
«no options specified» на пустой PUT. Конечное состояние задания
проверяется после имитации серверной обработки.

Ключевые round-trip-проверки (`tests/provider/test_harness_pve.py`,
`tests/ui/test_backup_job_dialog.py`):

- pool-задание: редактирование комментария → PUT только `comment` →
  перечитанное задание сохранило `pool`, `mailto` и не получило `vmid`;
- список VMID → правка списка → на сервере ровно новый список;
- `all=1` + очистка exclude → PUT `{"delete": "exclude"}` → на сервере
  `all` сохранён, `exclude` удалён;
- `all=1` → смена режима на pool → на сервере `pool`, без `all`/`vmid`;
- слово «all» в поле VMID отвергается формой (ValueError) и сервером
  (400) на обоих путях (POST/PUT);
- prune-backups: объект и строка проходят round-trip без схлопывания;
- дубликат id и удаление несуществующего задания → 400;
- PVE8-путь `/cluster/jobs` работает с тем же хранилищем заданий.

## 5. Fleet Health

- D4: `ClusterFleetReport.tasks_available` различает `tasks=None`
  (источник не собран) и `tasks=[]` (подтверждённая пустота). При
  недоступной истории гость без доказательств получает жёлтую строку
  «Backup state unverified» с текстом конкретной ошибки источника
  вместо красного «Never backed up». Прямые доказательства (PBS,
  подтверждённая история) работают как раньше — ошибка одного
  источника не уничтожает данные остальных.
- `tasks=[]` при собранной истории сохраняет честный красный
  «Never backed up» (подтверждённое отсутствие).
- D6: для кластеров с узлами ниже PVE 7.2 добавлена серая строка- caveat
  «Job-run attribution unavailable» (запуски заданий не несут job id в
  UPID) — объясняет, почему гости «только под заданиями» могут остаться
  непроверенными; не считается issue.
- D7: `_task_aggregates` пропускает строку задачи без какого-либо
  разборимого времени (нет `starttime` и пуст UPID-слот, либо мусор в
  поле) — одна повреждённая строка больше не роняет отчёт кластера;
  остальные строки агрегируются.

## 7. Что осталось неисправленным и почему

- **D5 (общий PBS между кластерами)** — не исправлен кодом. Надёжная
  привязка «снапшот → кластер» существует в принципе (кластер видит
  только те datastore+namespace, на которые ссылаются его pbs-хранилища),
  но требует протаскивания размерности `(datastore, namespace)` через
  весь контракт PBS-маппинга (сборщик → backend → domain) и проверки
  полей `datastore`/`namespace` в ответах `/nodes/{node}/storage` на
  живом PVE — по условиям этапа сетевые проверки запрещены, а
  придумывать эвристику по совпадению VMID аудиторски запрещено.
  Ограничение задокументировано комментарием KNOWN LIMITATION в
  `virtdeck/backend/fleet.py` и предложено отдельным этапом.
- Предупреждение `PytestUnhandledThreadExceptionWarning` в полном
  наборе — существовало до этапа (поздние потоки в таймаут-тестах
  безопасны по построению, см. 6.1.1), новых регрессий не вносит.
- Форма по-прежнему не покрывает все опции vzdump (mailto, performance,
  fleecing и т. д.) — сознательно: они гарантированно сохраняются
  (A4), а редактирование этих полей — отдельная работа.

## 8. Что требует решения владельца
