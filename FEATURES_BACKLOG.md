### B18. Разобраться с логикой дерева (левая панель)
Аудит и продумывание структуры левой панели: как организованы группы (B16),
кластеры, одиночные хосты, хранилища — что куда должно быть вложено.

**Аудит выполнен (2.10), фактическая структура (`tree_panel.py`):**
- Верхний уровень: пользовательские группы (B16) → секции «Clusters» →
  «Standalone hosts» → «Storage». Группы строятся из `cfg["group"]` (хост — своё,
  кластер — от любого участника).
- Кластер: агрегат `[r/t]` по всем ВМ кластера; внутри — элементы нод (листья:
  статус, тултип, заметка B19, без своих ВМ), затем группы пулов, затем ВМ без
  пула прямо на уровне кластера. Т.е. ВМ подняты на уровень кластера (view «по пулам»).
- Одиночный хост: пулы → ВМ; ВМ без пула — прямо под хостом. Модель вложенности
  отличается от кластера (там ВМ не под нодой).
- Пул может отображаться и под кластером, и под одиночными хостами (пул,
  размазанный по кластеру и standalone, виден в обоих местах) — осознанно.
- Storage: отдельная секция; в кластере — дедуп по имени («name (@cluster)»),
  отдельные — «name (host)». Хранилища не входят в группы и не вложены в хосты.
- Раскрытие дерева хранится по текстовым путям колонки 0 (суффикс `[r/t]`
  срезается); заметки B19 живут в колонке 1 и на пути не влияют.

**Найденные несостыковки (зафиксировано как follow-up, в 2.10 не трогаем):**
- Две модели вложенности: в кластере ВМ ищут на уровне кластера, у standalone —
  под нодой. Кандидат: переключатель вида кластера «по нодам / по пулам».
- Дедуп хранилищ кластера по имени маскирует per-node различия (same name,
  разное содержимое). Кандидат: раскрытие «name (@cluster)» → список нод.
- Группы B16 не включают хранилища; секция Storage игнорирует группы.
- Секции «Clusters»/«Standalone hosts» видны даже пустыми.
- Согласование с VISION.md (Site/Datacenter) — отложить до v3.x-проектирования.

**Follow-up закрыт (2.11, B20):** секции убраны (плоское дерево), хранилища
перенесены в режим «Хранилища», группы включают хранилища в этом режиме,
пустых секций больше нет. Остаются открытыми: две модели вложенности
(ВМ на уровне кластера vs под нодой) и раскрытие «name (@cluster)» → список нод.

#### Проработка «Universal Cluster Mover» (2026-09-11, PVE 7.x+)
Мотивация собственной реализации: зависимость от `remote_migrate`
(EXPERIMENTAL с PVE 8+, могут сломать без breaking-changelog) нежелательна;
фича нужна на PVE 7.x тоже (парк владельца: один кластер с PBS,
остальные standalone по России, SSH-доступ есть везде).

- **Гарантированный путь (по умолчанию, 7.x+):**
  1. vzdump снапшот-бэкап ВМ на source storage (`POST /nodes/{node}/vzdump`,
     snapshot mode) — running ВМ не останавливаем.
  2. SSH-транспорт архива source→target (факт: у PVE нет API полного
     скачивания vzdump-архива — только file-restore для файлов внутри
     архива + upload, поэтому SSH — основной транспорт). Варианты:
     - **Одноразовый restricted ключ — целевой вариант**: десктоп генерит
       одноразовую пару, публичник кладётся в `authorized_keys` dst с
       `command="scp -t /path"` (restricted command), приватник — временно
       на src; после операции ключ из authorized_keys и приватник удаляются.
       Скомпрометированная src получает ровно одну scp-команду в один путь,
       а не identity владельца. Цена: генерация/deploy/cleanup — код умеренный;
       restricted-command капризен в деталях (протокол scp, права каталога
       приёма) — проверить на живой ноде при разморозке (нужна тестовая
       инфраструктура).
     - **Agent forwarding** (простой fallback): `ssh -A src "scp file dst:/path"`
       — без инфраструктуры ключей, но осознанный tradeoff: скомпрометированная
       src-нода может использовать ключ владельца для auth куда угодно.
       Приемлемо только для доверенных PVE-нод.
     - **via-desktop** (последний fallback): `ssh src "cat file" | ssh dst
       "cat > path"` с десктопа — когда у src нет прямого сетевого пути к
       dst (гео-площадки без mesh); трафик идёт src → десктоп → dst
       (дважды через VPN).
  3. Create+restore на target (`POST /nodes/{node}/qemu|lxc` с `archive:`,
     стабильные эндпоинты, работают с 7.x; restore PBS в v2.12 уже реализован).
     Конфиг-маппинг: bridges/storages (автоподбор + ручная правка),
     `target-vmid`, MAC сохраняем (IP не потеряются).
  4. Cutover кнопкой: `stop` source → `start` target. Source остаётся
     как резерв; опция delete после проверки. Данные на момент бэкапа,
     downtime = время restore + старт.
- **Быстрый путь (опция):** native `remote_migrate` при PVE ≥ 8.0 +
  schema-проба метода — «Live (experimental)» с явным предупреждением;
  недоступен — мастер молча не показывает опцию (тест-контракт: мастер
  не падает на 7.x-фейке).
- **PBS-оптимизация:** если обе стороны имеют один PBS datastore
  (сценарий владельца) — restore прямо из PBS, SSH-транспорт не нужен.
- **Транспорт через PBS как замена SSH** — отвергнут как универсальный:
  PBS есть только на одном кластере владельца; решения по бэкап-инфраструктуре
  остальных площадок пока нет (могут появиться новые кластеры).
- **Зависимость:** SSH-движок `asyncssh` (новая зависимость) — общий
  с вехой M6 «Консоли» (SSH-терминал положит UI поверх готового движка).
- **Прогресс/отчёт:** task-UPID обоих кластеров, итоговый отчёт.
- **UX мастера (честные ожидания по времени):** размер архива известен
  из `ls` на source; до старта — замер скорости короткой probe-передачей
  и ETA «~N часов при текущем канале» (сотни ГБ по гео-VPN — часы;
  без ETA пользователь уходит спать и утром видит оборванную передачу).
  Поведение при обрыве VPN: `rsync --partial` через SSH, если rsync есть
  на обеих нодах, иначе честный рестарт с понятным сообщением.
- **Отвергнуто:** честная live-миграция с нуля (QEMU migration protocol,
  NBD-mirroring, QMP с обеих сторон) — нереалистично для соло-разработки,
  даже Proxmox держит это EXPERIMENTAL.
- **Идея на будущее (минимальный downtime):** zfs send/receive по SSH
  (внутрикластерный pvesr между кластерами не работает) — см. идеи ROADMAP.

### B24. Fleet Health ✅ (v3.0.0 — веха M4, киллер-фича)
Сводный отчёт по всем независимым кластерам сразу («весь парк одним
взглядом»): backup compliance, version drift, storage runway, snapshot
sprawl. Профиль целевого юзера: владелец нескольких площадок/кластеров
(MSP-паттерн). Ни один конкурент не даёт health несвязанных окружений
(PDM/ProxCenter — server+web для одной организации). Всё на стабильных
read-only API — ноль EXPERIMENTAL, идеальный противовес риску B21.

- **Backup compliance**: какие ВМ/CT не покрыты бэкап-джобом (`GET
  /cluster/backup`: schedule + vmid[]/pool/all+exclude — сопоставление
  чисто клиентское); «последний успешный бэкап» — из PBS vmaidx
  (фундамент v2.12), либо task history. **Matching-движок — отдельный
  доменный модуль (без Qt/API), table-driven юнит-тесты до UI**: самый
  коварный участок спеки (nested pool↔exclude пересечения, ВМ мигрирует
  между пулами между запусками) — false positive/negative здесь подрывают
  доверие ко всему Fleet Health с первого использования.
- **Version drift**: `GET /nodes/{node}/version` по всем нодам всех
  кластеров; подсветка отстающих (риск несовместимости при будущих
  cross-cluster операциях).
- **Storage runway**: тренды rrddata → прогноз «кончится через ~N дней»
  (capacity forecasting влилась сюда); ценность взрывается на cross-cluster
  виде: «у площадки Б кончится через 12 дней, остальные ок». Прогноз с
  доверительным интервалом — rrddata дырявый, наивная линейность врёт.
- **Snapshot sprawl**: `GET /nodes/{node}/qemu|lxc/{vmid}/snapshot` —
  1 запрос/ВМ (~10–20 с на парк 200 шт) → скан по кнопке + кэш, лимит
  параллелизма, не фоновый.
- **Partial failure (семантика зафиксирована до реализации)**: кластер
  offline → плашка «данные от HH:MM» (последнее известное состояние),
  отчёт не становится пустым и не падает целиком.
- **M4.0 — тестовый харнесс до фич**: fake PVE/PBS API + record/replay
  fixture'ы (фан-аут живыми кластерами не тестируем).
- Запуск из меню/трея; отчёт «что где красное» с переходом к объекту.

**Реализовано (v3.0.0):** matching-движок `virtdeck/domain/backup_coverage.py`
(vzdump-семантика: all > pool > vmid + exclude, templates exempt;
table-driven юнит-тесты) и агрегация `virtdeck/domain/fleet.py`; сбор/аналитика
`virtdeck/fleet/` (collector, drift, runway — прогноз наименьших квадратов
с 95% доверительным интервалом, sprawl — скан по кнопке с ограниченным
параллелизмом); воркеры `virtdeck/backend/fleet.py`; диалог
`virtdeck/ui/fleet_health.py` (частичный отказ → плашка «данные от HH:MM»);
харнесс fake PVE/PBS API (`tests/harness/`). Запуск: тулбар, трей,
Ctrl+Shift+F; двойной клик — переход к объекту в дереве.

### B25. Профили подключений — план v3.0 (веха M10 Платформа)
Сценарий: несколько площадок/организаций, работа через разные VPN; за раз
работают с одной организацией. Целевой юзер — владелец (админ своих
площадок); tenant-сущность сознательно не заводится (см. ROADMAP «НЕ в 3.0»).

- Справочник профилей в config.sqlite (минимально: имя + порядок).
- Поле профиля у cluster cfg; профиль «(все)» = текущее поведение.
- Активный профиль: переключатель в UI (панель/меню), автозапуск с
  последним.
- Кластеры вне активного профиля — скрыты из дерева и «спят» (без
  переподключений/фоновых воркеров); переключение профиля = пауза/резюме.
- Экспорт/импорт профилей — не в скоупе минимальной версии.

### B22. Maintenance mode — план v3.0 (веха M5)
Режим обслуживания ноды (аналог vSphere Maintenance Mode). Нативного в PVE
API нет — оркестрация выполняется нашим клиентом.

- Контекст-меню ноды «Maintenance mode…»: эвакуация running ВМ —
  live-миграция (`POST /nodes/{node}/qemu/{vmid}/migrate`) на целевые ноды,
  подобранные по загрузке из `/cluster/resources` (CPU/RAM/mem, локальные
  ресурсы дисков); для HA-ресурсов — `POST /cluster/ha/resources/{sid}/relocate`.
- Пометка ноды «обслуживание» в дереве (локально в ui_state/config):
  предупреждение/блокировка запуска новых ВМ на ноде на уровне UI.
- Прогресс по задачам, отчёт «что куда улетело» (нода → список ВМ/целей).
- Exit: снятие пометки; опционально «вернуть ВМ» по списку отчёта.
